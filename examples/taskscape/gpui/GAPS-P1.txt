Each gap: what happened, and what I would have wanted. "OWN" marks my own mistakes; "GPUI" a
limit of the framework (0.2.2); "P0" something in the contracts, the spec or the tauri target

== Start-up and total time ==

gpui:
  - start-up (launching the adapter to its reply to advertise): 0.2–0.3 s in the full checks
    (Xvfb, an X connection, GPUI's app; no window is opened until the render check). The first
    mount after it pays the Vulkan pipelines and the store: about 1 s.
  - a mount: 0.2–0.5 s (fixture in memory 0.05–0.1 s, a new GPUI window 0.1–0.2 s, settling).
  - total: the twelve contracts, 194 tests, took 3m51s on gpui in full check 3 (5m23s in full
    check 2, 4m28s in 1); tauri took 12m28s–13m41s for the same tests in the same runs. A behaviour
    test is 0.6–1.5 s; the slowest are the clips at full window size (llvmpipe draws a 1180×760
    frame in 15–40 ms, and a clip waits for each frame to be presented).
  - setup.sh: 11m29s from scratch on this machine (GPUI and its dependencies, a debug build
    with optimised dependencies, line tables only; 1.9 GB), then ~40 s after a change to the app.
tauri (P0's target, for comparison, same runs): start-up 0.9–2.7 s.

== Feasibility (the first 30 minutes) ==

- Version: the `gpui` crate 0.2.2 from crates.io (22 Oct 2025), pinned `=0.2.2`. It is the
  published, versioned release: a semver pin with a lock file, rather than a Zed commit that
  drags in the whole Zed workspace. Its one build problem: `xattr` 0.2.3 (under gpui's HTTP
  client) doesn't compile with libc 0.2.191; the lock file pins libc 0.2.186, the version the
  fixtures crate already uses.
- A window on a machine with no GPU and no display works: Xvfb, and GPUI's Vulkan renderer
  (blade) on Mesa's lavapipe (llvmpipe). Wayland was not tried; the X11 path is enough.
- Test support: `TestAppContext` and `VisualTestContext` (feature `test-support`) give simulated
  keystrokes and clicks and `debug_bounds` for `debug_selector`, but on a test platform that
  draws no pixels, and `debug_selector` is compiled only with `test-support`. So the target uses
  a real window instead: real X input (XTEST), pixels read back from the X server (XGetImage), and
  the app's own part tags for bounds. Screenshots, traces and clips are real frames.

== What omnicui or the contracts got in the way of ==

1. Parts without an accessibility tree (GPUI).
   GPUI has no accessibility tree, so a part's text, name, role and checked state are what the
   app declares in its part tag (src/parts.rs), next to the element that draws them; only the box
   is measured. The tag and the drawn text come from the same string in every case, but a check
   can't catch a part that draws one thing and declares another, which the DOM's innerText and
   AccessKit would.
   Wanted: nothing from omnicui; GPUI's planned accessibility support, when it lands.

2. Scale can't be traced, and isn't drawn (GPUI).
   GPUI has no transform for a box. "sheet-in" (scale 0.96 → 1 with a fade) is drawn as the card
   growing from 96 % of its width with the fade; the text inside doesn't scale. `trace.scale` is
   not advertised (with that reason). The sheet's and palette's opacity traces and clips pass
   against tauri (9–10 ms, 5–24 ms).

3. uniform_list can't hold the design's rows (P0 / prompt).
   The prompt asks for `uniform_list` for long lists, which measures one row and gives every row
   its height; DESIGN.md has two row heights (31.5 px, and 46 px with a notes line). The pane uses
   GPUI's other virtualized list, `list()` with a `ListState`, which keeps variable heights.
   Wanted: the prompt to say "a virtualized list".

4. No text input widget in GPUI (GPUI).
   GPUI 0.2.2 ships the text input API (`EntityInputHandler`), not a widget: Zed's editor is in
   another crate. src/text_field.rs is built on GPUI's input example, with wrapping for notes.
   Notes render as rich text (GPUI's StyledText: bold, italic, code, links, lists) and are edited
   as their source with Markdown marks (`**Friday**`), saved back as the sanitized HTML the store
   keeps. There is no formatting toolbar.

5. The capture bar's reference screenshots are blank (P0).
   tauri's capture screenshots are white pages (480×240, nothing drawn), though its behaviour
   tests pass: the tray card isn't painted when the screenshot is taken. So capture's colours
   (100 %) and layout (10.4 %) warnings compare the gpui card with nothing.
   Wanted: the tauri target's capture mount painted (P0 to look at).

6. The pane's round-check test (P0, fixed during my run).
   It first expected one taskCompleted and "4/8 DONE" for the brief, where the product's rule
   (and the Tauri app's toggleDone) completes the subtree: three events, "6/8 DONE". P0 changed
   the contract while I was running; it now matches.

7. DESIGN.md doesn't give the backdrop (P0).
   "Centred over a dimmed window" without the dim. The app's Backdrop is black at 30 %, fading
   in over 160 ms (common-ui Backdrop.tsx, tokens.css `.animate-scrim-in`), behind sheets and the
   palette. Until I matched it, every sheet and palette screenshot warned at 100 % (different
   backgrounds). Likewise the sheet's buttons (common-ui KeyAction: only a danger accept is
   filled) and the filter panel's layout (a select for Sort, accent-filled segments) are only in
   the code; the filter warned at 42 % layout until I redrew it from the screenshot.
   Wanted: DESIGN.md to list the backdrop, the key-action buttons and the segmented control.

8. The done lamp (P0, a design difference by direction).
   The review makes the round check mean done, so a done task's check is the done lamp (filled
   `done-lamp-1` with a tick). The Tauri app shows that lamp only while ⌥ is held; normally a done
   task's check is an empty ring. The long list (every fourth task done) warns on colours in dark
   (78 %: the lamp's blue is most of the solid drawing). The other pane screenshots pass at 0 %.

9. Generated keyboard checks and GPUI's own keyboard click.
   GPUI clicks a focused element on Enter or Space key-up. A key binding that also pressed it
   ran the press twice (switches toggled back: two failures until fixed, OWN 3). The target says
   which keys activate what in advertise (`keys`). Settings has the same 14 not-measured keyboard
   checks as tauri (GAPS-P0 11).

10. The run folder is shared (omnicui).
   `.omnicui/run/` is per project, and P2 ran checks of the same project at the same time: its run
   replaced my folder during a check ("the target replied, but wrote no picture" for my render
   check). Every gpui run since uses `--out` outside the repository.
   Wanted: a run folder per invocation (or per target set), or a lock with a clear message.

11. The fixture loader is slow on a busy disk (P0's loader, the app's Store).
   Each fixture is ~60 SQLite commits; with another agent compiling, a mount took 0.8–7 s. The
   adapter writes fixtures under /dev/shm when the system has it (0.05–0.3 s). The loader still
   sets HOME for the whole process (GAPS-P0 13), so mounts are one at a time.

12. Motion that GPUI draws at the machine's pace.
   llvmpipe draws a 1180×760 frame in 15–40 ms, so real-time traces were coarse and noisy (the
   palette's opacity trace measured 10 ms in one run and 26 ms in the next). Clips and traces now
   run on the app's own animation clock (src/motion.rs), held and stepped 16 ms per frame, as
   the tauri target steps the page's animations for its clips; and a frame is captured only
   after the next one is drawn, because the renderer presents a frame after GPUI paints it (a
   picture taken at once showed the frame before: the project menu's clip measured 71–83 ms
   against tauri, 20 ms after). The protocol says a trace is "sampled every frame": these are the
   app's frames on its own clock, not the screen's.
   Wanted: a trace or clip reply that can say its clock was stepped (as `held` says for clips).

13. The inspector's rise against tauri's (a real difference, in the port's favour).
   After a press on a subtask, tauri's drawer is drawn at opacity 0 for about 50 ms (three
   frames) before its 110 ms rise starts: the webview renders the new task and loads its notes
   first. The port draws the new task in the next frame and rises at once. In the inspector's
   round-trip trace (out to 0, back to 1) that gap is the difference: 17–32 ms against a 20 ms
   threshold. The window's trace of the same rise (one way) passes at 4 ms. I didn't copy the
   delay: it is the load time WHY.md is about.

14. Text a test types is ASCII (the target).
   XTEST types through the server's US keymap; the adapter refuses a character it has no key for,
   with the character in the error. No contract types one.

15. DESIGN.md's capture-bar motion is gone from the app (P0).
   DESIGN.md says the notes panel "grows open (a grid-row transition)"; the tray's NotesSection
   has no transition now, it opens at once. My 180 ms growth measured 78 ms apart on the clip;
   the port now opens it at once too (1.5 ms). The card's layout followed the tray's own
   screenshot (title flush left, the notes under a hairline, the shortcut glyphs on Clear and
   Screenshot): 9.2 % layout in the focused run, from 10.4 %. Not ported: the notes' formatting
   toolbar (gap 4).
   Wanted: DESIGN.md corrected.

16. The project menu's clip (open).
   Its opacity trace matches tauri's to 0.6 ms in every run, but its clip measures 20–92 ms
   apart from run to run. Part of it was GPUI drawing a box's shadow under the box (CSS draws it
   only around): while the menu was translucent its own shadow darkened it, so the picture first
   went darker, then lighter. The shadow now comes in as the card becomes opaque; the clip then
   measured 26 and 57 ms in two runs. The rest I haven't found; the menu's box is 220 px wide
   where tauri's is narrower, and `record: {part}` measures 8 px around it.

== Decisions someone may want to revisit ==

- Settings is drawn in the main window, over it, as a 640×520 panel ready on its first frame
  (WHY.md allows that or a native window). Mounted on its own (the contract), it is the same view
  with its title bar; its close reports `windowAction {close}` there and closes the panel in the
  window.
- Window controls: macOS keeps its own traffic lights at the leading edge (the bar leaves them
  84 px); elsewhere the app draws minimise, zoom and close at the trailing edge, as Zed does on
  Linux. DESIGN.md: "the platform's own".
- The capture bar is in the same process as the main window (`--capture` opens it), so it needs
  no HTTP between processes; the Tauri tray's HTTP server is not ported.
- The capture bar mounted at 480×240 paints the area under its card in the card's colour; the
  app's pop-up window is the card's size.
- Notes are edited as their Markdown-marked source and shown as rich text (gap 4).
- Fixtures go to /dev/shm when it exists (gap 11).

== What is ported, and what isn't yet ==

Ported, in SPEC-PRODUCT.md's order: the task pane, the preview rail (inspector, draft, several
tasks), the capture bar, the title bar, the whole window, sheets, the palette, Settings, the
filter panel, the Trash, the toast, the row menu. Keymap generated from the hotkey catalog (with
the user's overrides, re-bound when Settings changes one), application menus, focus handles for
the keyboard (arrows, Tab/⇧Tab, Space, ⌥Space, Enter/F2, Escape, type to search), GPUI's
virtualized list, the client-side title bar (macOS keeps its traffic lights; Linux gets
minimise/zoom/close at the trailing edge, as Zed draws them), motion on one clock (rise, sheet-in,
panel-in, the backdrop, the notes panel), reduced motion.

Not ported yet:
- The capture bar's global ⌘↩ and the menu-bar icon: GPUI has no global shortcuts or status
  items; `taskscape-gpui --capture` opens the bar as a pop-up window, and Escape minimises it. Placing it at the pointer
  and over every Space is the platform's and not done.
- Screenshot capture: the app's own (macOS screencapture through taskscape_common); elsewhere it
  fails as the Tauri app does ("Capture failed").
- The attachment lightbox (image and text previews); a copied file's tile does nothing yet.
- Drag and drop (rows, tabs, attachments), resizing the rail and the split.
- Import and export of a list as JSON ("Import JSON…" opens the file dialog and stops there).
- Renaming a tab in place (double-click asks with the rename sheet instead); renaming and
  deleting a project from its menu.
- Search scope (this list, the project, all): the options button cycles the fields only.
- The menu's labels for a selection ("Copy N tasks"); Move in the bulk bar opens the menu's
  list submenu.
- @mentions in notes, and a formatting toolbar (gap 4).
- The done check's drawn tick (160 ms after 80 ms): the lamp fills at once.
- Reduced motion forced by the system or Low Power Mode.

== OWN: my mistakes ==

1. I ran my first checks into the project's shared run folder (gap 10) and took a render-check
   failure for a bug in my probe.
2. The first mounts closed the last window, and GPUI's X11 platform ends the app then: every test
   after the render check was "broken". An 8×8 window in the screen's far corner keeps it alive.
3. I bound Enter and Space to press a focused button, on top of GPUI's own keyboard click
   (gap 9): the two Settings switches toggled twice.
4. "Type a letter to search" listened on the task list, so typing into the subtask field inside
   it moved the focus to the search field after the first letter.
5. Traces started at the first frame after the press: GPUI draws nothing while nothing changes,
   so the resting state was missing and the rise looked like a different motion (∞ and 180°
   warnings). The trace now draws two frames first.
6. Clip frames taken as soon as GPUI had painted, before the renderer presented them (gap 12).
7. A button with two `.hover()` styles: GPUI asserts on that in a debug build, and three
   comparison runs broke on it.
8. I first drew the backdrop, the sheet buttons, the filter panel and the capture card from
   DESIGN.md's prose and memory instead of the app's components (gaps 7 and 15).
9. The build folder grew to 11 GB (full debug info and the incremental cache) past the 10 GB
   asked for, until I slimmed the profile.
10. Adapters that panicked left their Xvfb running, and killed ones left lock files until no
   display number was free (a whole comparison run broke on it). Xvfb now dies with the adapter,
   and a lock whose process is gone is reused.
11. Progress notes written with times I guessed rather than read; corrected from the clock.
