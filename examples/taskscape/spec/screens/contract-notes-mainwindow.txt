# How the app.mainwindow contract was written, and what its props make the harness do

BASIS. Merged from Draft A (with its notes) and Draft B (with its notes), and corrected by the critique. Sources named by the drafts: spec/inventory/main-window.json, features-main-window.txt, notes-main-window.txt, spec/screens/web.md, spec/decisions.md, library/contract-format.txt, library/index.txt, and grepped feature records (area-08, area-09). I did not open the files myself; the merge works from the draft texts and the critique. Where a fix needs a source value that is not in the drafts, the value is flagged below.

PROPS (merged harness meaning). Only one prop: dataset (string, default standard). The harness signs in as the demo account on the real API and loads the named set before mounting. standard = Home (Errands, Reading, Garden) and Spring launch (Website, Press kit), opening on Home > Errands. empty = Home with one empty list, Inbox. nolists = Home with no lists. long = standard plus 40 more tasks in Errands. Only the empty, nolists and long tests override it, through the per-test props. Split, preview state, sheets, trash, palette and Settings are reached by steps, the way a user reaches them. Draft A's splitList prop is dropped (see drops).

EVENTS. events: {} because the inventory lists no outward event for this screen.

ROLES. Row titles, the project and list menu items, and the account menu items are buttons (aria menuitem, tab or option mapped to button). Menus, dialogs, containers and the aside are generic. Toast is status; StatsBar count is generic, because the role rule maps only toast and progress to status (Draft B's status on doneCount was changed). Separators are slider (Draft B's own judgement, kept with the comment). Heading is used for titles.

KEYS. One vocabulary for the whole file: KeyboardEvent.code style (KeyN, Digit2, Slash, Comma, BracketLeft, BracketRight, F2, Escape, Delete, Enter, Space, Arrow keys), modifiers joined with +. Draft A's character style ('/', 'N', 'K', '2') was rewritten to match. Control stands for the web Mod key. The macOS Mod-to-Meta mapping is not defined in the files read and is flagged.

CONFLICTS RESOLVED OR RECORDED.
1. Toolbar Settings button: Draft A says it is replaced by the account menu; Draft B keeps it. Critique says keep it; kept.
2. Which list the Split view button opens: Draft A says the toolbar does not record it; Draft B asserts Reading in the right pane, and both drafts use the Reading split as the reference split-view state. Kept Draft B's check, flagged as an assumption.
3. Row titles: Draft A had row as a button; Draft B had row as a generic container with the title as a button. Kept both: row is generic (container), rowTitle and the other row titles are buttons.
4. doneCount role: status in Draft B, generic in Draft A. Set to generic (see roles).
5. Sheet fade: Draft A traces opacity. Draft B says motion classes are not applied (F11-030). Critique asks for a decision. Dropped the trace: the sources do not confirm the fade, and the critique's scale part is also unconfirmed.
6. Settings size and shape: web.md modal (640x520) followed; the notes reply that Settings "routes to a settings page" is set aside. Size is not asserted because expect has no size field.
7. Delete-key behaviour: Draft A has a confirmation step; Draft B has none. Kept the confirmation (decision 10). The Delete binding itself is assumed.
8. Control+Comma: Draft B's note says its hint is dropped with the web Settings route; critique says test it. Kept the test, flagged.
9. Names: "Delete list" name on dialogDelete (feature record F09-009) is used, and Draft B's sheetConfirm name (not in the sources) is dropped. "Cancel" (F09-094), "Create" (web.md) and "Undo" are sourced names; "Move to Trash" and "Open Trash" come from decision wording. Names not in the sources are not asserted: trash, commandButton, accountButton, trashClose, bulkMarkDone, openSelection, settingsClose.
10. Row More menu contents are not recorded; only that it opens.
