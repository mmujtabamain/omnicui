# Review notes on the command-palette screen (the team's comments and how each was settled)

- [desktop] Haiku critic: The Scrim (Backdrop2 with dim="soft") and the Overlay's outside-mousedown dismissal assume the palette sits over a dimmed main window. The desktop rebuild must not dim the main window, so the palette should become its own borderless window placed near the top centre of the app window, with dismissal on outside click mapped to window blur or focus loss (F06-018). The 490 px panel geometry and the 12vh top offset still apply to that window.
  - reply (Haiku review): Decided. Decided: on desktop the palette is its own borderless window with no scrim, because dialogs are separate windows with no backdrop dimming. It dismisses on Escape, on window blur (the focus-loss pattern the reference uses for menus), and after a command runs; scrim-press dismissal does not apply on desktop. Keep the reference geometry: 490px wide (35rem at 14px), the 60vh list cap, and the 12vh top offset, placed top-centre of the main window.
- [web] Haiku critic: The web build cannot rely on the ⌘K opener, and browser shortcuts take precedence. The inventory notes the opener binding was never captured (F08-010), so the web spec must pick and document an in-page opener. Several HotkeyHint values shown in the rows (⌘F Search this list, ⌘N New task, ⌘⇧N New list, ⌘⇧P New project, ⌘Z and ⌘⇧Z Undo and Redo) collide with browser chords and would be swallowed by the browser, so the web hints need a separate check.
  - reply (Haiku review): Needs Mujtaba. The opener needs a product decision: one reviewer decided a visible in-page control with no dependency on ⌘K, the other says the opener is open, and the brief does not settle it. The hint decisions are settled: ⌘F, ⌘N, ⌘⇧N are browser-reserved and are not shown on web rows, ⌘⇧P should be treated the same unless checked, and ⌘Z and ⌘⇧Z stay because the page receives them outside text fields. The remaining hints (⌘\, ⌘,, ⌘⌥S, ⌘⇧H, ⌘⌥-, ⌘⌥=) must be checked against the browser before the web spec ships.

Question: How should the web build open the command palette, given ⌘K is browser-reserved and its opener binding was never captured: (a) a visible in-page toolbar control only, (b) an in-app chord that browsers do not reserve, documented in the web spec, or (c) both?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 7: Opening the command palette on the web: both a visible control (a search-and-commands button in the title bar) and Ctrl/Cmd+K, captured while the page has focus (pages can take this chord from the browser).
- [both] Haiku critic: The MenuItem variant with a HotkeyHint is 32 px tall, but the variant without a hotkey is 30 px tall, and nothing in the spec explains the 2 px difference. Mixed rows in the same list therefore misalign, which reads as an inconsistency. One row height should be used for both variants, or the spec should record why they differ.
  - reply (Haiku review): Decided. Decided: every MenuItem uses one row height of 32px, the measured height of the hotkey row (box 488x32). MenuItem sets only padding, so the no-hotkey rows, recorded at 30px with no measured box, grow to 32px so mixed lists align. The palette rows get one min height so the two variants match.
- [both] Haiku critic: The 'Delete "<task title>"' row (F06-034) appears only when a task is selected, but none of the three reference states shows it, and the inventory gives no hotkey or look for it. The MenuItem entries therefore leave its appearance unspecified. The spec should add a palette state with a selected task so the conditional row can be built and checked.
  - reply (Haiku review): Answered. The Delete row is already specified by the source. It is pushed only when a task is selected, after the Manage rows under a repeated Task heading, with label Delete “<task title>” in curly quotes, group Task and no accelerator, so it uses the no-hotkey MenuItem with no hint. One reviewer reads the source as icon delete while F08-044 lists delete against Open Trash, so confirm the icon at palette.ts:157-164 before building; a selected-task recording would verify the row but is not needed to build it.
- [both] Haiku critic: Feature F08-049 is titled 'Palette list runs past its panel', yet the Palette panel is overflow-hidden and the Results list scrolls at the 60vh cap. The palette state's Open Trash and list and project rows are recorded as clipped below the panel edge, which conflicts with scrolling. The rebuild should decide whether clipping is intended, and the scroll cap should be kept in both versions.
  - reply (Haiku review): Answered. The scroll is intended and the clipping is an inference. The results list is overflow-y-auto inside a flex column capped at 60vh, and the palette state's 456px panel is exactly 60% of the 760px window, so rows past the cap scroll rather than clip. Keep the 60vh cap and overflow scroll in both builds, and drop the word clipped from the inventory since F08-049 records it only as inferred.
- [both] Haiku critic: The Overlay's behaviour section covers only Escape and outside dismissal. It omits focus return to the opener on close (F06-088), the suspension of the app key map while the palette is open (F06-087, F08-061), and the parking of focus on the scrim (F06-089). The Backdrop2 scrim is also named as a component that CommandPalette.tsx does not import, so the rebuild cannot map it to a real component. Both gaps need to be closed before the rebuild.
  - reply (Haiku review): Answered. All three gaps are real and covered by the features. Add focus return to the opener on close (F06-088; overlay.ts:104-107, 146-149) and focus parking on the scrim when nothing inside asks for focus (F06-089; overlay.ts:109-114), where the palette input autofocuses so this is only a fallback. The depth counter (F06-087; overlay.ts:11-25) gates only Escape and printable keys, so arrows, Tab, Space and Enter still reach the app map (F08-061; useAppKeyboard.ts:185-309); CommandPalette.tsx imports no Backdrop2, so map the web scrim to the Backdrop rendered inside Overlay (Overlay.tsx:99-111) at dim soft, and note the desktop build has no scrim.
