# Review notes on the attachment-lightbox screen (the team's comments and how each was settled)

- [desktop] Haiku critic: The scrim region and the Overlay dialog (dim strong, blur, placement fill) model the lightbox as a modal layer over the main window. The desktop build is offline and uses separate windows for dialogs, so the lightbox should open as its own window with no backdrop dimming or blur of the main window, and Close or Escape should close that window. This matches feature F04-052, which the desktop version should reinterpret.
  - reply (Haiku review): Decided. Decided for the desktop build: the lightbox opens as its own window with no scrim and no blur over the main window, because desktop dialogs are separate windows. Close and Escape close that window, and a click on the empty stage closes it too, as in the reference, so both builds share one close rule. F04-052 is reinterpreted this way for desktop.
- [both] Haiku critic: The scrim click behaviour is unresolved: the inventory says it is unconfirmed whether a bare click on the Backdrop2 surface closes the lightbox, and Overlay is set to dismissOn none. The rebuild needs an explicit decision for both versions, since the stage div is the only confirmed click-to-close target and F04-053 says the lightbox closes on backdrop click.
  - reply (Haiku review): Answered. The source answers this: a click on the empty stage closes the lightbox. dismissOn none removes the Overlay scrim's press handler, but the panel's children fill the window and the stage div has onClick=onClose, so only the top bar, media and chevrons are excluded. Escape also closes through useDismissable, and both builds keep this rule (desktop closes the separate window), while the running-app check in F04-053 is still open.
- [both] Haiku critic: The Previous and Next chevrons are sized inconsistently: the code class h-11 w-11 gives 44px, while the measured buttons are 39x39. The variant should be fixed to one size in the rebuild rather than left to whichever source is used, and the chosen size should be noted in the chevron widgets.
  - reply (Haiku review): Not a problem. The 44px figure is wrong for this app: the root font size is 14px, so h-11 w-11 (2.75rem) renders at 38.5px, matching the measured 39x39. Both chevrons use the same class, so there is no size conflict, and the rebuild uses h-11 w-11 on the shared chevron widget at 1rem = 14px.
- [both] Haiku critic: The top bar height conflicts: the code uses h-13 (52px) while the measured bar is about 40px with 28px controls at y 9. The rebuild should pick one height for the top bar region, since the 12px difference changes where the stage starts and how the image is centred.
  - reply (Haiku review): Decided. Decided: the top bar uses h-13 (3.25rem), which is 45.5px at the 14px root, not 52px as a 16px root would give. A 28px control centred in 45.5px sits at y 8.75, matching the recorded y 9, so the measured 40px bar is the outlier and the recording should be re-measured against h-13.
- [both] Haiku critic: The Remove attachment button is styled as a danger action only on hover (danger background, white glyph); its default state is the same neutral white-at-70% glyph as Rename and Reveal. A destructive action that is indistinguishable at rest from safe actions is an inconsistency, and the default state should carry the danger tone or the difference should be stated.
  - reply (Haiku review): Decided. Decided: the Remove attachment glyph carries the danger colour at rest, so it does not look like Rename or Reveal until hover. Hover keeps the danger background with a white glyph from the code, because destructive actions use the danger colour.
- [both] Haiku critic: The same job, opening the attachment externally, is done by two different widgets: the Open externally icon button in the top bar (onMedia, 28x28) and the primary Button with the text Open externally inside the fallback card. The rebuild should use one shared component or a single variant so the two entry points look and behave the same.
  - reply (Haiku review): Decided. Decided: one shared Open externally widget with the onMedia variant serves both entry points, and the variant is set once in the shared library. The top bar shows it icon-only, and the fallback card shows the icon with a visible Open externally label in place of the primary Button. Accent blue stays reserved for the primary action and selection, as the brief requires.
- [web] Haiku critic: The Reveal in Finder button calls api.revealAttachment to open a local file manager, which does not exist in a cloud app where files live on the server. The web version should drop this button, or replace it with a download action, and keep Open externally as the only way to leave the app.
  - reply (Haiku review): Decided. Decided: the web build drops Reveal in Finder, and the Reveal item in the tile menu too, because a cloud app has no local file manager and the reference hides the action for remote files. No download action exists in the reference, so none is added, and Open externally stays the only way to leave the app.
- [web] Haiku critic: The window-level capture keydown handler for ArrowLeft and ArrowRight calls stopPropagation and runs before native controls, so it can take arrow keys away from the audio and video controls and from the selectable text preview. The web build should scope the arrow handling to when no media or text element has focus and should leave browser shortcuts in charge.
  - reply (Haiku review): Decided. Decided: on web, ArrowLeft and ArrowRight step attachments only when focus is outside a native video, audio or text preview control, and the handler does not stop propagation there, so native controls keep those keys. The reference listens in the window capture phase and stops propagation for every arrow key whatever the target, which conflicts with the brief rule that browser shortcuts take precedence.
