# Review notes on the settings-capture screen (the team's comments and how each was settled)

- [web] Opus (orchestrator): The Capture pane is about screen capture and the capture bar; neither exists on the web, so this pane is dropped there.
  - reply (Haiku review): Decided. The web build drops the Capture pane. Every control in it is screen capture mode or the local screenshots folder, and the brief gives web no capture window and no screenshots. Desktop keeps the pane.
- [web] Haiku critic: The whole Screenshots group (SettingsGroup, Segmented "Capture mode", footnote hint, and the "Saved to" PathButton) depends on screen capture and a local folder, which the web build does not have. The web version should drop this group and the Capture tab, or replace them with something that has a server-side meaning. The Capture tab and its links should not appear in the web sidebar without that change.
  - reply (Haiku review): Decided. On web, drop the Screenshots group (Capture mode segmented control, its footnote and the Saved to row) along with the Capture tab and its link, since the brief removes screen capture and local folders from web. No server-side replacement is proposed, because it would be new scope rather than a fix to this pane. Desktop keeps the group.
- [desktop] Haiku critic: The "Saved to" SettingRow with its PathButton should stay on desktop. It opens the screenshots folder in the OS file manager and falls back to the nearest existing ancestor when the folder does not exist yet, which the inventory records as PathButton.tsx:10-12. The desktop build should keep that fallback for its local SQLite data folder.
  - reply (Haiku review): Decided. The Saved to row stays on desktop, since the brief removes capture only from web. The nearest-existing-ancestor fallback lives in the Rust open_path command rather than in PathButton, which only documents it, so the shared PathButton keeps the fallback for the local data folder rows too.
- [both] Haiku critic: The inventory shows no window-level discard control in the Settings title bar. TitleBar is recorded with trailing=false, but the features list requires a Discard-all (undo) button in the title bar that appears after any change (F10-027, F13-061). The inventory should add it as a trailing control, or state why it is absent.
  - reply (Haiku review): Answered. The Discard-all control exists in the reference and is shown only when something has changed. SettingsWindow.tsx:198 sets the changed flag and :209-227 render the undo button as the title bar's trailing slot, placed before the window controls at SettingsTitleBar.tsx:15-16. The inventory's trailing=false reflects the unchanged recording, so the inventory should record the changed state rather than add a control.
- [both] Haiku critic: The sidebar search field (InputWell with TextInput2) has no clear button in the inventory. Its trailing slot is empty, but F10-011 requires an x clear button while the query is non-empty. The inventory should show that state and its widget.
  - reply (Haiku review): Answered. The clear button exists and renders only while the search query is non-empty, as an IconButton labelled Clear search. clearSearch resets the query and scope, so the empty trailing slot in the inventory reflects the empty-query recording, and the inventory should add the non-empty state rather than a new widget.
- [both] Haiku critic: The "Screenshots" heading is recorded twice at the same box (172,58, 100x16): once as the SectionHeader span and once as a muted Label. These are one widget. Keep one heading component so the header style is defined in one place.
  - reply (Haiku review): Answered. The uppercase eyebrow and the muted Label are one nested element, not two, because SectionHeader renders its label as a Label child. Keep SectionHeader as the single heading and drop the separate Label entry. The Shortcuts inventory counts its three group headings the same way and should be corrected too.
- [both] Haiku critic: Hints on the two setting rows are inconsistent. "Capture mode" explains itself in a footnote under the control (Label as=p, 11px). "Saved to" uses a description under its title (Label, 11.5px). Use one pattern for row explanations in this pane and in the other panes.
  - reply (Haiku review): Decided. Keep the two placements that SettingRow defines: Capture mode's value-dependent hint goes in the footnote, and Saved to's static 'Click to open the folder' stays in the description. Use one 11px caption token for both, which replaces the 11.5px description size and matches the SectionHeader hint.
- [web] Haiku critic: The traffic-light cluster (WindowControls/MacLights, close, minimize and fullscreen lights) belongs to the macOS window chrome. A browser tab has its own controls, so the web version should not render these lights. The inventory also contradicts itself on the two inert lights: the code says inert=true, while the elements.json state reads disabled. F10-029 says inert, so the rebuild should follow that.
  - reply (Haiku review): Decided. The web build renders no window lights, because a browser tab has its own controls and the brief gives web no window chrome. On desktop the two lights are inert, as F10-029 says: the inert prop sets the DOM disabled attribute, so the inert and disabled readings describe the same control.
- [desktop] Haiku critic: The inventory's measured size (title bar 1180x46, tabpanel 1026x715) conflicts with F10-001, which says the Settings window opens at a fixed 640 x 520. The desktop build should be a separate window at the fixed size from F10-001. The recorded size should be checked before it is used as the layout reference.
  - reply (Haiku review): Answered. The reference opens Settings at 640 x 520, so the inventory's 1180 x 760 window and 1026 x 715 tabpanel cannot be the layout reference. Whether the window is fixed or resizable with a 640 x 520 minimum is the open question raised on seed-settings-shortcuts-7.
