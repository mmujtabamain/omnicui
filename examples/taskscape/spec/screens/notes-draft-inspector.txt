# Review notes on the draft-inspector screen (the team's comments and how each was settled)

- [web] Haiku critic: The Screenshot DashedButton (runDraftAction 'shot') and the helper paragraph 'take a screenshot' depend on screen capture, which the web build does not have. Keep the feature title F04-012 (the button creates the task with an attachment), but on web the button should take an uploaded image file, and the helper copy must change to match.
  - reply (Haiku review): Needs Mujtaba. Both reviewers agree the desktop Screenshot stays a native capture, since F04-034 is flagged system and F04-012 notes the same conflict. They differ on the web slot: Reviewer A proposes an image picker on the existing Attachments file path that creates the task as Untitled only after a file is picked, while Reviewer B says the brief rules out capture but does not settle what the slot becomes. The F04-012 retitle and the helper copy in F04-013 wait on that product call.

Question: On web, what should the Screenshot slot in Start with become: (a) removed, with the helper copy changed to match; (b) an image upload that creates an Untitled task with the file through the server upload, reusing the Attachments file picker (Reviewer A's proposal); or (c) no new control, with Attachments as the only web file route?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 5: Draft's Screenshot slot on the web: replaced by Image: paste an image (Ctrl/Cmd+V) into the draft, or pick a file. It creates the task (as "Untitled" if it has no title) with the image attached, uploaded to the server. Desktop keeps Screenshot.
- [web] Haiku critic: The title bar's traffic-light window controls (Light close, minimize, fullscreen) and the drag_indicator grip are window chrome that a browser tab already supplies. The web build should drop them, while the desktop build keeps them.
  - reply (Haiku review): Decided. Both reviewers agree that web drops the traffic-light controls and the drag grip, and desktop keeps both. The reference already renders the three window controls only when isMac and otherwise shows a spacer, so web follows that pattern. The traffic lights are native window controls (F07-085), and the grip is pointer-events-none with no action (F07-086).
- [web] Haiku critic: The draft is defined as existing before any database row, and Escape, Discard or click-away must write nothing. On web this has to be client-side state that is only sent to the server when Enter, blur with a title, or Note/Screenshot commits it, because the backend is multi-user and a dropped draft must not leave a server record. The rule for the draft action guard (F04-119) also needs to hold across the network request.
  - reply (Haiku review): Answered. The reference writes no row until a commit: the draft lives in uiStore.draftListId, cancel and empty-title commit only clear it, and a row is written only by the commit, Note, or Screenshot paths. A click-away with a title commits (F04-005), so the no-write rule covers only an untitled draft with nothing added (F04-118). The double-row guard is draftBusy, set before the first await and cleared in finally, so on web the flag must stay set until the network response returns (F04-119).
- [both] Haiku critic: The Discard draft IconButton uses the last_page icon, which reads as navigation (next page) rather than discard. Its purpose is only clear from the tooltip. Pick a discard or close glyph for both builds, or accept the tooltip as the only label.
  - reply (Haiku review): Decided. Use the close glyph with the Discard draft tooltip in both builds, at the default IconButton variant with iconSize 16, because discard writes nothing and is not destructive. The reference already uses close for neutral dismissal (Clear selection), and the Delete list close stays distinct through its danger variant. last_page is dropped because it reads as next page.
- [both] Haiku critic: The two DashedButtons in 'Start with' are inconsistent: the Note button uses an add icon at size 16, while the Screenshot button uses screenshot_monitor at size 15. Both sit in the same row and do the same job, so the icon size should be the same, with the glyph difference the only variation.
  - reply (Haiku review): Decided. Both Start with buttons use icon size 16. Note's add icon is already 16 and the Discard button is 16, so the Screenshot glyph moves from 15 to 16 and only the glyph differs between the two. This holds whichever way the web Screenshot slot is resolved.
- [both] Haiku critic: The code and the measured values disagree for the Start with buttons (className h-10 gives 40px, but the rendered height is 35px) and for the helper paragraph (leading-4 gives 16px, but the rendered line height is 14px). The rebuild has to choose one value for each and record it, instead of leaving the two sources to conflict.
  - reply (Haiku review): Not a problem. The comment's 40px and 16px readings assume a 16px root, but the reference sets html font-size to 14px, so 1rem is 14px. h-10 is 2.5rem (35px) and leading-4 is 1rem (14px), so record 35px for the Start with buttons and 14px for the helper line. F04-013 also lists text-[10.5px] where the source is text-[12px], so the source value is the one to record.
- [both] Haiku critic: The empty 20x20 completion ring placeholder is non-interactive, yet it looks like the round Select checkbox used on every task row. Its purpose (a placeholder for the ring the task will have) is not clear from the screen, so the rebuild should either label it or drop it, and avoid implying that it toggles done.
  - reply (Haiku review): Decided. Both reviewers agree to remove the empty ring placeholder from both builds. It is an empty h-5 w-5 rounded-field box with no state or handler, and its checkbox role is only inferred (F04-009, corrected by check). The round check is the picked state (F07-056) and the done toggle is the row checkbox (F04-027), so removing the placeholder removes a lookalike control.
