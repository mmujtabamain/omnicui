MERGED HARNESS MEANING OF EVERY PROP
- dataset: the harness loads that demo set into the one local SQLite database before launch. standard is the default. The desktop seed data is assumed to match the web demo data in spec/screens/web.md; this is not confirmed.
- open: main (default) = booted, main window shown, bar hidden. background = launch with the main window hidden, bar hidden, agent running (used by the tray Open test). Draft A's open: boot value is moved to the boot prop, because the boot veil is a launch phase, not an open state.
- boot: done (default) = boot finished, veil and box removed. held = the harness withholds the first paint, so the veil and box stay up for the reads. No step releases it. The stalled value from Draft B is dropped: egui has no frontend and no ready signal, so the 4 s fallback has no meaning here.
- focus: main = the main window holds keyboard focus, so chords go to main (decision 11). other = the harness makes another app's window the OS-focused one before the step. Chords then go to the global handler, and to the bar when it is shown. On an input step with focus other, the part only names the window the test reads. The key itself is an OS-level global key event, not a part action.
- barState: hidden (default) = bar parked, as in F14-029. shown = the harness shows the bar and then moves OS focus to another app, so the bar is visible without keyboard focus. Renamed from Draft B's captureBar, because a prop and a part should not share a name. The focused value is not needed: the typed-summon test covers the focused bar.
- lastProject, lastList: stored as last_active_project and last_active_list before first paint. "" stores nothing, and the app opens on Home > Errands.
- captureMode: writes the screenshot_mode setting (fullScreen or region).
- captureHotkey: bound keeps the default toggle combo. unbound clears the toggle binding.

EVENTS
- shellCommand {action}: the shell's command to the main window. import_list and export_list come from the List menu. new_task comes from the toggle chord with main focused; the action name is not asserted (see the conflicts). attach_screenshot comes from the screenshot chord with main focused. refresh comes after a submitted capture (F14-046, F15-030).
- captureSubmitted {title}: the capture just submitted from the bar.
- quit {code}: exit code 0 on every quit path (tray Quit, closing the main window). Hiding the bar is not a quit.
- remembered {list, project}: the store write of last_active_list and last_active_project (F15-039, uncertain).
- Naming: action values use snake_case (import_list, attach_screenshot). Input names use camelCase (toggleCaptureBar, captureScreenshot). Draft B's menuCommand event (hyphenated values) and its attachScreenshot input name are dropped in favour of this set.

PROPOSED NAMED INPUTS (none exists yet; each needs a platforms.yaml entry)
- toggleCaptureBar: default { key: Control+Enter }, macos { key: Meta+Enter }. Mod is Control on Windows and Linux and Command on macOS (web.md); decision 20 uses Enter. The reference default conflicts across sources: docs say Cmd+Return, the code comment says Cmd+Enter, F15-028 says Cmd+Enter. Confirm the exact default when platforms.yaml is written. The tooltip test accepts any label. Delivered to the app's global-hotkey handler, as the OS would deliver it.
- captureScreenshot: default { key: Control+Shift+Enter }, macos { key: Meta+Shift+Enter }. Reference is Cmd+Shift+Return (docs) or Cmd+Shift+Enter (code).
- closeWindow: default { key: Alt+F4 }, macos { key: Meta+KeyW }. The OS close request to the named window. On Linux the window manager may consume Alt+F4; if so, the close-to-quit tests are not measured there.
- Existing named inputs used: switchList2, nextTab, nextProject.

DECISIONS FOLLOWED
- Decision 2: close, minimise and zoom controls are never tested. Reading taken: the app's response to a close request (quit, or hide for the bar) is app behaviour and is tested through closeWindow. The two drafts read decision 2 differently; the team should confirm this reading.
- Decision 11: with main focused, the main window handles the chord and the bar is not shown. This overrides F14-001's visible-first order.
- Decision 20: Enter in the title submits; the global toggle acts only when the bar lacks focus; a visible unfocused bar is hidden by the toggle; Escape hides. This overrides F14-001 and F14-002's visible-first reading.
- Decision 21: one egui process. Tray and hotkeys are in-process handlers. The reference routes and ports (7420, 7421, /focus, /quit, /new-task, /attach-screenshot, /refresh, /reload-hotkeys) are not asserted. Their behaviour is kept as handlers and shellCommand events. The mechanism (Tauri, emit_to, tray-app) is replaced by muda and tray-icon.

CONFLICTS AND HOW THEY WERE RESOLVED
1. Tray menu. The brief lists Open, Refresh and Quit. The source has only Open Taskscape and Quit Taskscape (F14-041, F14-042; the drafts also cited tray/src-tauri/src/lib.rs:205-217, unchecked). Refresh is the shellCommand emitted after a capture (F14-046, F15-030), not a tray item. The brief's author should be told.
2. F14-001 versus decision 20. Followed decision 20. F14-002's own title says a visible bar is hidden.
3. F13-016 (Cmd+Enter in the title dismisses) versus decision 20 (submits). This contract follows decision 20; the capture-bar card owner must resolve F13-016. The test that depends on it is marked.
4. Hotkey labels differ (⌘Return, Cmd+Enter, ⌘Enter). The tooltip regex accepts any label; the inputs use the platform modifier form.
5. Boot box. The records describe an empty 25x25 box at the window centre, removed on boot done. No tick is recorded anywhere; Draft B's "ticking" has no source. The test asserts unchecked and does not assert a tick.
6. Boot veil and box in the egui build. Presence is unconfirmed (critic). The parts are marked optional: true, and the boot tests stay. If the egui build keeps no veil, remove the two boot tests, the two parts and the boot prop.
7. F15-039 (remembering the list) is uncertain in the record. The remembered tests are kept and marked; the trigger is inferred from the list tabs and the project pill.
8. F14-040 (tray left click) conflicts between code and docs. The tray icon is OS-drawn, so it is left out.
9. The tooltip wording is unverified (critic), so the regex was loosened to ^Taskscape.+capture$. The exact text is not asserted.
10. The "first list" fallback is uncertain (project or all projects), so the test asserts only the remembered project in the target.

OWNERSHIP
- This contract owns the bar's box (captureBar), the title (captureTitle) and the target (captureTarget) only for shell outcomes: visibility, focus on summon, submit routing, and target text and press. The card contract owns their behaviour. Part ids are per screen, so the two contracts do not clash on accessibility ids.
