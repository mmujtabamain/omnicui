# Review notes on the main-window screen (the team's comments and how each was settled)

- [desktop] Opus (orchestrator): Desktop windows open as real windows where a desktop app would open one (Settings, sheets, the lightbox), not as layers inside the main window.
  - reply (Haiku review): Decided. Agreed by both reviewers: on desktop, Settings, the New list, New project, rename and delete sheets, and the attachment lightbox each open as their own window with no backdrop, under the brief's rule that new windows open where a desktop app would. Settings is already a singleton window (F15-023), while the reference's sheets go through the in-window SheetHost and the lightbox is drawn inside TaskInspector, so these are rebuild changes. The web build is not covered by this rule.
- [both] Haiku critic: No widget in the main window opens the Trash, although the TrashPane is in the aside (App.tsx:121-124) and the features list soft delete, restore and Empty Trash (F15-008 to F15-012). The title bar, search bar and footer have no Trash control, and the inventory says the opening control is not in its files. Add an explicit entry point, such as a Trash button in the title bar or a footer item, so both rebuilds have a defined route to restore and empty deleted tasks.
  - reply (Haiku review): Needs Mujtaba. The reference's only route to Trash is the command palette's Open Trash command, since palette.ts:146 is the only setTrashOpen(true) call, so the inventory's 'not in these files' misses it. Reviewer B adds a web-only title-bar Trash button because browser shortcuts take precedence over the palette shortcut (F08-010), while Reviewer A treats any on-screen Trash control as a product call the brief does not settle.

Question: Where should Trash be reachable on the main window: (a) the command palette only on both builds, as in the reference; (b) a Trash icon button in the title bar on web only, with the palette on desktop; or (c) a Trash icon button in the title bar on both builds?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 1: Trash entry point: a Trash icon button in the title bar on both versions, as well as the command palette's Open Trash.
- [both] Haiku critic: The Show completed tasks toggle (F11-053, with shortcut F08-015) has no widget on this screen. The footer holds only the ViewControl, which opens the filter panel, and the search bar has no completed-task toggle. Decide where the toggle lives, because done tasks stay in place (F09-090) and the reference shows them struck through.
  - reply (Haiku review): Answered. The reference has no main-window control for the global show-completed toggle: it is the Show completed tasks row in Settings > General, the 'Show / hide completed' palette command, and the toggle_completed shortcut (Cmd+Shift+H, F08-015). The filter panel's All / Active / Done segment is a per-pane filter, not this toggle, and done tasks keep their place (F09-090). The rebuild keeps these three placements and adds no title-bar or footer control.
- [both] Haiku critic: The same tune glyph opens the same Filter and Sort panel from two places with different labels: the search-bar IconButton titled 'Search options' (iconSize 15) and the footer ViewControl titled 'Sort & filter' (size 14). Pick one name and one icon size, or document why the search-field entry and the footer entry differ.
  - reply (Haiku review): Not a problem. The search-bar tune button does not open the Filter & Sort panel: it opens the scope and fields menu through ScopeFields, titled 'Search options', and only the footer ViewControl titled 'Sort & filter' toggles the panel. The inventory entries that say the search button opens filter-panel (main-window.json:868 and :1322) should be corrected, so the proposal to give both buttons one name and size does not apply.
- [both] Haiku critic: The same add glyph has different variants for no clear reason: the New list IconButton uses iconWeight 300 and a 5.25 px radius at size lg, while the New task IconButton uses iconWeight 400 and a 4.375 px radius at small size. Likewise, the delete-list close icon uses iconWeight 500 but the split-close close icon uses iconWeight 300. Unify the icon weight and radius per button size in the rebuild.
  - reply (Haiku review): Decided. The variance is real in the source: New list is size lg with icon weight 300 and a rounded-md class, New task is the default md with weight 400, delete-list close is weight 500, and split close is weight 300. The radius difference is a Tailwind rounded-md override (5.25px), not a token, so the rebuild removes per-call weight and radius overrides. Each IconButton size gets one icon size, one optical weight from the theme, and one radius token (4.375px for sm, md and lg; 7px for xl), and the F11-099 note that no weight-500 close icon exists is wrong.
- [both] Haiku critic: The window-control spec conflicts. The MacLights widget (Close, Minimize, Full Screen) is listed on the main window, and F09-058 and F11-060 say it is present there, but F15-037 says traffic-light buttons are hidden on the main window. The web build should not draw macOS-style dots over the browser chrome, and the desktop build should use the native OS window controls, so resolve which one the reference actually shows before the rebuild.
  - reply (Haiku review): Needs Mujtaba. This is not a true conflict: the reference hides the native traffic lights on the main window (lib.rs:1001-1005) and draws the MacLights on macOS and the WinControls cluster elsewhere (TitleBar.tsx:49,105), so F09-058, F11-060 and F15-037 agree. Reviewer B's option (c) misdescribes the reference split, since the reference also draws Windows controls. Web draws no window controls because the browser owns the window, and the desktop choice is a product call the brief does not settle.

Question: For the desktop main window, should the window controls be (a) drawn controls on every desktop platform with native buttons hidden, as the reference does; (b) native OS controls on every platform; or (c) drawn macOS controls with native controls on Windows and Linux?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 2: Desktop window controls: native OS controls on every desktop platform; the app draws none. The web draws none either; the browser owns the window.
- [desktop] Haiku critic: The SheetHost overlay, mounted at App.tsx:144, renders the New list, rename and delete-list sheets inside the main window, and these dim the window behind them. In the desktop build each sheet should open as its own window with no backdrop dimming, as the Settings window already does (F15-023). The New list and delete-list buttons in the title bar and tabs should open those windows instead of an in-window sheet.
  - reply (Haiku review): Decided. Agreed by both reviewers: in the desktop build the New list, New project, rename and delete actions each open as their own window with no backdrop dimming, following the brief's rule and the Settings window model (F15-023). The reference routes these through openSheet, askText and askConfirm into the in-window SheetHost with a scrim (F11-027), so the New list, per-tab delete and rename paths all need window targets.
- [web] Haiku critic: The toolbar tooltips advertise shortcuts such as 'Settings ⌘,' and 'Hide preview panel ⌘\' (F08-041), and the command palette and other global bindings are also defined. In the web build browser shortcuts take precedence and there are no global hotkeys, so these hints must be re-checked against the browser and the bindings that survive should be listed, or the hints dropped. The Settings button should route to a settings page rather than opening a separate window.
  - reply (Haiku review): Decided. The hints come from the hotkey map: the preview tooltip shows Cmd+Backslash and the Settings tooltip shows Cmd+Comma. Per the brief, the web build registers no global hotkeys and browser shortcuts take precedence, so each in-page hint is kept only if the browser does not reserve its binding (checked during web setup), and the Cmd+Comma hint is dropped with the web Settings route. The palette accelerators follow the same rule, and the web Settings button routes to a settings page instead of calling the desktop window command.
- [web] Haiku critic: The main window starts hidden and reveals in stages, with a boot veil that fades out after the data loads (F15-033, F09-036, F09-037). The inventory has no loading widget and the boot overlay is unconfirmed in App.tsx. The web build fetches data from the server, so it needs a defined loading state for the task area and the list tabs, with an error state when a request fails.
  - reply (Haiku review): Decided. The boot veil is an in-page overlay (index.html:137, faded by boot.ts after initialLoad), so the web build keeps it fading after the first load, as in the reference, and the reference's missing error state (dismissBoot runs in finally with no catch) is filled in. Later requests show a loading state in the task area and tabs, a failed request shows an inline error with a Retry action, and the desktop staged reveal (F15-033) is dropped for web. Reviewer B's view that web drops the veil is not followed, because the veil is not a native-only mechanism.
