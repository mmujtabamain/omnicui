# Review notes on the toast screen (the team's comments and how each was settled)

- [both] Haiku critic: The auto-dismiss timer has no widget or behaviour in the inventory. F06-095 requires the toast to auto-dismiss after 6 seconds, F06-096 requires a new toast to replace the current one and restart the timer, and F06-097 requires Dismiss to cancel the timer, yet the inventory only says the duration is not shown in the evidence. Add the timeout as a stated behaviour of the Toast wrapper, including the restart and cancel rules.
  - reply (Haiku review): Answered. The reference defines the timer: toastStore.ts:26 sets 6000 ms, show() clears the previous timer before replacing the toast (lines 24-25), and dismiss() clears it (lines 29-30). So a new toast restarts the 6 s timer, and Dismiss or Undo cancels it. The reference timer does not pause while the pill is hovered or focused, so the web spec should record that gap, since keyboard users can lose Undo after 6 s.
- [both] Haiku critic: The after-undo state contradicts the code. Toast.tsx:31 dismisses the toast after Undo runs, and F07-077 says Undo restores the task, but the after-undo recording still shows the pill with the same message. The spec should decide whether the pill is removed on Undo and treat the recording as stale, or whether the toast stays and the code changes, instead of leaving this as an open question.
  - reply (Haiku review): Answered. The source settles this: Toast.tsx:29-32 runs toast.action() and then dismiss() in the same click, so Undo removes the pill. The after-undo recording that still shows the pill is stale, and the feature list already records that conflict. The same capture also disagrees on the restored count (tree shows 7 tasks, screenshot shows 8), so both after-undo captures should be re-taken before they are used as evidence.
- [web] Haiku critic: The Undo ToolbarButton has no keyboard path in the web build. The reference relies on Cmd+Z (F07-017, F07-079 hint text) for the same job, but browser shortcuts take precedence in the web version, so the Undo button must be the only route to undo from the toast. Do not carry the Cmd+Z hint into the web toast.
  - reply (Haiku review): Decided. The toast carries no Cmd+Z hint, since Toast.tsx:21-36 renders only the message, Undo and Dismiss, so nothing is stripped from it. The Cmd+Z hint is in the Move to Trash sheet detail (tasks.ts:77, 114), which is a separate sheet. In the web build the Undo ToolbarButton is the toast's only undo control, a native button reachable by Tab, Cmd+Z is not relied on, and no web-only route is added; the desktop build keeps the palette Undo item (F06-028) as a second route.
- [web] Haiku critic: The Undo action in the web version is a server call, so it can fail, but the toast has no failure state. Toast.tsx:31 calls toast.action() and then dismisses, while F07-018 says a failed undo leaves the command on the undo stack. The web Toast needs an error message or a retry path, because the pill would otherwise disappear and the trashed task would stay in Trash with no explanation.
  - reply (Haiku review): Needs Mujtaba. The reference calls undo() with void (tasks.ts:36-39), so a rejected call is unhandled, the command stays on the undo stack (history.ts:48-58; F07-018), and Toast.tsx:29-31 dismisses the pill at once. One reviewer decided on option (a) for the web build, while the other treats failure feedback as a product call that the brief and decisions do not settle, so it goes to you.

Question: When a web Undo call fails, should the toast (a) stay open until the undo succeeds, showing an error with Undo as the retry and Dismiss still closing it, (b) swap its message for a short error and auto-dismiss after 6 s as usual, or (c) dismiss silently as the reference does and leave the task in Trash?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 11: Undo fails on the web: the toast stays, shows the error, and Undo becomes "Try again". Dismiss still closes it.
- [both] Haiku critic: The message label has only one observed value, "Moved to Trash", but F07-034 defines a bulk delete toast and F07-031 counts only root items in the single-task label. The inventory gives the Label no variants for counts or other actions, so the spec should list the message formats each caller supplies, or the Label will be built with a single hard-coded wording.
  - reply (Haiku review): Answered. The label is not hard-coded: Toast.tsx:22 renders toast.message as supplied by the caller. The two callers are 'Moved to Trash' for a single delete (tasks.ts:82) and '<n> moved to Trash' for a bulk delete, where n is the root count (tasks.ts:120; F07-034). The 'Delete N task' text in F07-031 is the undo command label and is never displayed (F07-021), so the spec should list the two message formats and their callers.
- [both] Haiku critic: The toast pill sits over the footer row of the task-list pane, which holds the progress footer (F07-101, 2/8 DONE and 25%). The inventory does not say whether the pill must avoid covering that footer or may overlap it, and the pill's pointer-events handling makes the overlap clickable in the strip. Decide the placement rule explicitly for both builds, since the web layout will vary with window width.
  - reply (Haiku review): Decided. The wrapper is pointer-events-none (Toast.tsx:14, 19), so only the pill takes clicks and the footer outside it stays clickable; the premise is partly wrong. Both builds keep the reference placement, a fixed bottom-centre overlay, and the pill (x 477 to 702, y 702 to 743) covers only empty footer centre at reference width, clearing the Sort and filter button (x 12), the done counter (x 52) and the percentage (x 820). The pill must never cover the Sort and filter button or the percentage; where a narrow window would force overlap, the pill rises above the footer, which replaces the earlier acceptance of overlap on narrow web widths.
- [general] Haiku critic: The Dismiss IconButton carries a title and aria label of "Dismiss" in code, but no visible tooltip appears in either recording, and the Undo button has no tooltip at all. The two buttons in the same pill therefore differ in how their purpose is exposed, so the spec should state one rule for tooltips on toast controls and keep the Undo and Dismiss labels consistent.
  - reply (Haiku review): Decided. Icon-only toast buttons carry a title that serves as both tooltip and accessible name, because IconButton sets no aria-label of its own, so the inventory's 'aria label' should read 'name from title'. Dismiss keeps title 'Dismiss' (Toast.tsx:42), and Undo keeps its visible label with no tooltip (Toast.tsx:25-35). The missing tooltip in the recordings is a capture gap, since hover states were not recorded, not a spec decision.
