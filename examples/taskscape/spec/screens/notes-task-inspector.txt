# Review notes on the task-inspector screen (the team's comments and how each was settled)

- [web] Opus (orchestrator): Screenshot attachments (the Shot button) are desktop only. On the web, attachments are files uploaded to the server and links.
  - reply (Haiku review): Decided. Agreed. The web has no screen capture, so the Shot button, which captures the full screen, is desktop only, and web attachments are server uploads and links.
- [general] Haiku critic: The Attachments header 'Link' ToolbarButton has no title or accessible label, while the empty-box 'Add a link' button has title 'Link a file or URL without copying' and the same job is described with different wording. Give both entry points one label and one tooltip, for example 'Add a link', and add the missing accessible name to the header button.
  - reply (Haiku review): Decided. Agreed. Both Link entry points get the tooltip and accessible name 'Add a link'. The header Link button keeps its short visible text 'Link' to save space, and the empty-box button keeps its visible 'Add a link' text.
- [both] Haiku critic: Adding a note has two controls with different variants for the same action: the 'Note' ToolbarButton (icon add, shown only when notes exist) and the full-width DashedButton 'Add note' (shown only when there are none). Both call setAddingNote(true) and the labels differ ('+ Note' versus 'Add note'). Pick one control and one label, or state explicitly that the dashed button is the empty-state variant of the same control.
  - reply (Haiku review): Needs Mujtaba. Both controls call setAddingNote(true), but the labels differ: the header button shows 'Note' with an add icon and the dashed box shows 'Add note'. The label 'Add note' is decided for both, but the brief's one-widget-per-job rule conflicts with keeping a dashed variant, and dropping a reference feature is a product call for the owner to make.

Question: Should the dashed empty-state 'Add note' box stay as a separate widget? Options: (a) keep it as a documented dashed variant of the shared 'Add note' button, recording the exception; (b) drop it and show the header 'Add note' button in the empty state too, which drops F03-026 and F04-074; (c) keep both as in the reference and document the empty state as a separate control.
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 4: Empty "Add note" box: kept, as the dashed variant of Button, used for every empty "add something here" slot (notes, attachments), so the exception is one documented variant rather than a separate widget.
- [web] Haiku critic: The Attachments 'Shot' ToolbarButton, its Spinner state and the 'Capture the full screen and attach it' tooltip depend on screen capture, which the web version does not have. Remove the button and its capturing state from the web build, and leave the Attachments header with File and Link only.
  - reply (Haiku review): Decided. Agreed, and this duplicates seed-o5 for the Attachments header. On the web, remove the Shot ToolbarButton, its Spinner state and the 'Capture the full screen and attach it' tooltip, so the header keeps File and Link only.
- [web] Haiku critic: The 'File' ToolbarButton and the 'Copy a file' empty-box button open a native file dialog and call api.addCopy with a local path. In the web version these should open a browser file picker that uploads the file to the server, and the 'Reveal in Finder' context-menu item should be replaced by a download action since no local file exists. The Link flow should accept URLs only, because a local path cannot be resolved on the server.
  - reply (Haiku review): Decided. Agreed. On the web, File and Copy a file open a browser file picker that uploads to the server instead of the native dialog and api.addCopy path, and Reveal in Finder becomes a Download action. The Link flow accepts URLs only, because the reference prompt's 'absolute path to a file on this Mac' cannot be resolved on the server, and Download is recorded as a web-only addition with no reference feature.
- [both] Haiku critic: The lightbox widget (AttachmentLightbox) has count 0 and no recorded state, so the inventory does not show its previous and next chevrons, position counter, top-bar name and kind icon, top-bar buttons, or rename and remove actions, even though the feature list keeps them. Add a widget entry for the lightbox internals, and for the mention autocomplete and attachment chip, so the rebuild has something to match.
  - reply (Haiku review): Answered. The reference does record the lightbox, so the inventory's 'state none recorded' is wrong: F04-052 to F04-058 and F04-065 cover the backdrop, chevrons, position counter, top-bar name and kind, top-bar buttons, and rename and remove. The mention chip and autocomplete entries already exist at count 0, so reviewer A's view that they are missing is not followed; the inventory needs the lightbox entries filled from these features and the mention counts updated from F03-040 to F03-044, and F04-065 says remove confirms while F04-058 records none.
- [both] Haiku critic: The Delete task IconButton (title 'Delete task', variant danger) has no recorded destination: its behaviour says it calls requestDeleteTask, and the confirmation sheet or Trash path is not verified. The feature list keeps 'Delete task button' as a must-keep feature. Confirm whether the web and desktop versions should ask for confirmation before deleting, and record the answer on this widget.
  - reply (Haiku review): Answered. The reference answers the destination: Delete task calls requestDeleteTask, which opens the 'Move to Trash?' confirmation with Cancel and the accept button, then shows the 'Moved to Trash' toast with Undo. Both versions keep this confirmation, with the desktop version as a separate window, and the accept label becomes 'Delete' per the vocabulary decision in seed-task-list-2, replacing 'not verified' on the widget.
- [general] Haiku critic: The done checkbox in the header uses size md (18px, check glyph 14px), but the subtask checkbox uses size sm (16px, glyph 12px) for the same job of toggling done. Nothing in the screen explains the difference, so use one checkbox size for done toggles or document why the subtask row is smaller.
  - reply (Haiku review): Decided. Decided: one done-checkbox size, sm at 16px, for the header, the subtask rows and the list round check, so every done toggle matches. Reviewer A's md at 18px for the header and subtasks is not adopted because it would leave the list check at a different size, and the 28px subtask pitch fits either size.
- [desktop] Haiku critic: The lightbox is described as a full-window overlay with a dimmed blurred backdrop, and the rename, link and remove flows use askText or askConfirm sheets. In the desktop version, dialogs and sheets must be separate windows with no backdrop dimming, so the lightbox and these flows should open as their own windows instead of an overlay over the inspector.
  - reply (Haiku review): Decided. Agreed for desktop: the lightbox opens as its own window with no dimmed backdrop in place of the reference's full-window overlay, and each rename, link and remove askText or askConfirm flow opens as a separate window. Escape closes the lightbox window, the backdrop-click close has no window equivalent and is dropped, and the web keeps the overlay.
