# Review notes on the settings-general screen (the team's comments and how each was settled)

- [both] Opus (orchestrator): The reference opens Settings as its own window. Desktop: keep it a separate window. Web: a /settings page in the app, not a modal.
  - reply (Haiku review): Decided. Decided: desktop keeps Settings as its own fixed-size window (640x520), as the reference does. On web, Settings is a /settings route page rather than a modal, because the web build has no separate windows, and window chrome and Escape-to-close are desktop-only.
- [both] Haiku critic: The title-bar undo IconButton and the Appearance and Tasks group clear controls promise to discard changes, but feature F10-030 says settings persist as soon as they change. The inventory never says what discard restores once a value is already written, so the rebuild needs a defined rule (for example, a pre-open baseline written back) before these controls can be built.
  - reply (Haiku review): Answered. The source defines this: each setting is restored to the value it had when the window opened (F10-027, with the baseline taken on first load per F10-033). Settings write through and persist at once (settings.ts:100-114, F10-030), so discard is a second write of the open-time value through the normal set path. The group clear control does the same for its own group's changed settings (F10-034; settings.ts:125-132).
- [both] Haiku critic: Two controls use the same undo icon for different scopes. The title-bar undo (trailing IconButton, tooltip "Discard every change made since this window opened") discards settings and hotkeys together, while the SectionHeader clear control (clearTitle "Discard changes made since this window opened") discards only its own group. The tooltip wording is also nearly identical, so the two should be given distinct labels or one icon and scope.
  - reply (Haiku review): Decided. Decided: both controls discard, so they keep one undo glyph and one widget, but each label names its scope. The title bar control reads 'Discard all settings and shortcut changes since this window opened' (aria label 'Discard all changes'), and the group header control reads 'Discard changes in this group'. The current near-identical wording cannot tell them apart.
- [web] Haiku critic: The sidebar has a Capture tab (screenshot_monitor icon) and a Shortcuts tab (keyboard icon), but the web version has no capture window, no screenshots and no global hotkeys, and tasks are added by hand. Those two tabs and their search coverage (F10-052) should be dropped from the web nav, leaving the tablist and ArrowDown/ArrowUp wrap order to match the remaining panes.
  - reply (Haiku review): Needs Mujtaba. The Capture tab is dropped on web, since its rows are desktop screenshot settings and the brief has no screenshots, and the About pane's Data folder rows (F10-038, F10-039) open a local folder, so they go too. Whether the Shortcuts tab stays is open: its Global and Capture bar scopes go on web, and dropping the whole tab also removes its search coverage (F10-052) and leaves General and About in the nav.

Question: On web, should the Shortcuts tab (a) be dropped entirely, leaving General and About, (b) keep the 31 Main window rows as a read-only list, or (c) keep them rebindable with any combo the browser reserves excluded?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 15: Shortcuts on the web: the Global group is removed (a browser cannot have global hotkeys). In-app shortcuts stay and can be changed; the recorder refuses chords the browser keeps for itself and says so.
- [web] Haiku critic: The Reduced motion row's forced-state logic and footnotes (variant A for Low Power Mode, variant B for macOS Reduce Motion) depend on native OS signals the browser cannot read. On web the Toggle should follow only the browser prefers-reduced-motion query, and both footnotes and the lowPower/systemPrefers disabled state should be removed.
  - reply (Haiku review): Needs Mujtaba. The Low Power and macOS Reduce Motion footnotes and the forced, disabled state go on web, since the browser cannot read those native signals. The browser's prefers-reduced-motion setting keeps applying through the CSS block (tokens.css:326-333), as the reference already treats the system setting. Whether the toggle mirrors the browser query, becomes an overridable account preference, or is removed is a product call the brief does not settle, and one view reads it as the user's own switch that does not follow the query.

Question: On web, should Reduced motion be (a) a read-only mirror of the browser prefers-reduced-motion query, (b) a stored account preference that starts from the browser query and can be overridden, or (c) removed from the web build?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 16: Reduced motion: a three-way choice like Theme: System (follow the OS), On, Off. On both versions.
- [web] Haiku critic: The title bar with macOS traffic lights (WindowControls), the drag region and the Escape-closes-window gesture (F10-024) only make sense for a separate desktop window. In the web version Settings should be a routed page with a plain heading, and Escape should not try to close the browser tab.
  - reply (Haiku review): Decided. On web, Settings is a routed page with a plain heading, not a window, so it has no traffic lights, drag region or fixed 640x520 size. Escape clears a non-empty search and otherwise does nothing, so it never tries to close the browser tab. The reference's Escape-closes-window rule (F10-024) is desktop-only, and browser shortcuts take precedence.
- [web] Haiku critic: The search shortcut Cmd+F / Ctrl+F (F10-025) collides with the browser's own find, and browser shortcuts take precedence in the web build. The web search field needs a different focus shortcut or should accept the browser find behaviour, and this should be decided before the field is built.
  - reply (Haiku review): Decided. Decided: the web build does not override Cmd+F or Ctrl+F. The browser's own find takes that key, since browser shortcuts take precedence, and the search field stays reachable by click and Tab with no other focus shortcut added. The web handler must not call preventDefault for these keys, while desktop keeps F10-025 as it is.
- [web] Haiku critic: Theme, Reduced motion and Show completed tasks are stored as local preferences in the desktop reference (F10-064 broadcasts show_completed across windows, F11-009 saves theme between launches). In the multi-user cloud app these values belong to the account and must sync across devices, and a failed save must be surfaced to the user rather than silently ignored as F10-031 does.
  - reply (Haiku review): Needs Mujtaba. Decided: on web, a failed save is shown next to the control and the control reverts to its last saved value, instead of failing silently as F10-031 does on desktop. Whether Theme, Reduced motion and Show completed tasks belong to the account or the browser is a product call: the reference keeps Theme and Reduced motion as local preferences (reducedMotion.ts:54-58, F11-009) and shares only Show completed tasks across windows (F10-064), while the cloud brief could put all three on the account.

Question: On web, should Theme, Reduced motion and Show completed tasks (a) all be stored per account so they sync across devices, (b) store Theme and Reduced motion per browser and Show completed tasks per account, or (c) all stay per browser as in the reference?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 17: Where settings are kept on the web: Theme, Reduced motion and Show completed tasks are stored per account, so they follow the user across devices. Desktop keeps them locally.
