# Review notes on the settings-shortcuts screen (the team's comments and how each was settled)

- [web] Opus (orchestrator): Global shortcuts (the Global group) cannot exist in a browser, and several macOS chords are taken by the browser. The web keeps in-app shortcuts only, with web-safe defaults.
  - reply (Haiku review): Needs Mujtaba. The Global part is settled: the web build drops the Global scope (toggle_capture_bar and screenshot_capture) because the brief gives web no global hotkeys. The web defaults for Main-window chords that browsers reserve are not settled, including Cmd+N (hotkeys.rs:345), Cmd+F (:351), Cmd+1 to Cmd+9 (:375-423) and Cmd+Shift+[ and ] (:441, :447).

Question: For the Main-window chords that browsers reserve (Cmd+N, Cmd+F, Cmd+1 to 9, Cmd+Shift+[ and ], Cmd+Alt+Left and Right, Cmd+Shift+N), should the web build (a) keep the Mac defaults and show those rows as unavailable, (b) remap each to a chord the browser does not reserve, or (c) remove those commands from web, given that Reviewer A treats this as an open product choice and Reviewer B would decide it now by assigning web-safe defaults without naming the chords?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 18: Browser-reserved chords on the web: remapped to web defaults. New task Alt+N; New list Alt+Shift+N; Search "/" when no text field has focus; Switch to list 1–9 Alt+1…9; Previous and next list tab Alt+Shift+Left and Right; Previous and next project Alt+Shift+[ and ]. Desktop keeps the reference defaults.
- [both] Haiku critic: The title bar has no Discard-all (undo) button, though F10-027 says one appears in the title bar after any change. The inventory's TitleBar variant (trailing=false) and its regions show only the three window lights and the Settings label. Add a trailing discard control to the title bar, or record where F10-027 lives if it is not on this screen.
  - reply (Haiku review): Answered. The title-bar Discard-all (undo) control exists in the reference, but only while something has changed. SettingsWindow.tsx:198 sets the changed flag and :209-227 render the undo IconButton as the trailing slot only then, placed before the window controls at SettingsTitleBar.tsx:15-16. The inventory's trailing=false reflects the unchanged recordings, so the inventory should record the changed state rather than add a new control.
- [both] Haiku critic: The sidebar search field (InputWell with Icon search and TextInput2) has no widgets for its effects. F10-011 (clear-x button), F10-015 (match count badge on each section), F10-016 (dimmed sections), F10-017 and F10-018 (section click scopes or clears the search), F10-020 (no-match empty state) and F10-021 (intro hidden while searching) are all absent. The inventory marks the filter behaviour as uncertain, so these need entries before the rebuild.
  - reply (Haiku review): Answered. Every search effect is in the reference, and the inventory missed them because its recording had an empty query. The clear button renders only while the query is non-empty, tabs show match badges and dim when they have no matches, and the intro is replaced by a no-match EmptyState while searching. The inventory should add a searching state rather than treat these as missing widgets, and the matching rule is F10-013.
- [both] Haiku critic: The group-level discard control conflicts with the feature list. SectionHeader (clearIcon undo, active=false) is never rendered in any state, and the inventory cannot say whether it is hidden or only shown when changed. F10-034 and F10-050 describe a group header dot that marks changed groups and discards only this session's rebinds, and no dot widget appears in the inventory. Choose one mechanism, undo icon or dot, and give it a visible rule.
  - reply (Haiku review): Decided. The group discard is the undo IconButton in SectionHeader, shown only while that group has changed since the window opened. The accent dot that SectionHeader draws when active has no handler and is dropped, because the brief reserves accent blue for primary action and selection. F10-034's 'click the dot' is therefore wrong, and F10-050 already names the undo button as the trigger.
- [both] Haiku critic: The selected state of the active Shortcuts MenuItem is inconsistent between captures. The default state gives a neutral fill of oklch(0.32 0.02 262 / 0.09), while the scrolled and recording states give blue oklch(0.6 0.2 255 / 0.1). The same selected tab should have one fill across states, so pick one value and confirm it against the design source.
  - reply (Haiku review): Answered. Every selected state uses the blue selection fill, bg-selection-1l (--selection-1l, oklch(0.6 0.2 255 / 0.1)). The neutral --wash-2l value is used only for hover, so the neutral default-state capture was a hover, and the Capture tab should get the same correction.
- [web] Haiku critic: The Global SettingsGroup (Capture bar and Screenshot capture rows, with the hint "work anywhere in macOS") and the Capture bar SettingsGroup (Clear capture draft row) depend on global hotkeys and a capture bar, which the web version does not have. Remove these groups and their rows from the web build, and drop the macOS hint. Keep the Main window group and its 31 rows.
  - reply (Haiku review): Decided. On web, remove the Global group (two rows, with the 'work anywhere in macOS' hint) and the Capture bar group (Clear capture draft), since those are the global toggle, screenshot and tray-only commands the brief removes from web. The Main window group stays with its 31 commands. Desktop keeps all groups, and its hint, which is hard-coded to macOS, should follow the platform.
- [web] Haiku critic: The recording keycap (Keycap with recording=true, Type shortcut prompt) captures every keydown, but in the browser combos such as Command-F, Command-T and Command-W are reserved and cannot be recorded. F10-025 (Command-F or Ctrl-F focuses search) collides with browser find. Browser shortcuts take precedence, so the web build must drop the search-focus shortcut or mark browser-reserved combos as not recordable.
  - reply (Haiku review): Decided. Browser shortcuts win on web, so the web build removes the Settings Cmd/Ctrl+F search-focus shortcut and refuses to record a combo the browser reserves, such as Cmd+F, Cmd+T, Cmd+W and Ctrl+F. The refusal uses the existing red footnote under the recorder row, and the sidebar search field (F10-009) remains the way to search Settings. Whether the Main-window Cmd+F row ships with a default is left to the open question on the browser-reserved chords.
- [desktop] Haiku critic: The window size conflicts between sources. The inventory gives the Settings window as 1180x760 at 0,0 (Window and SettingsWindow entries), but F10-001 says the window opens at a fixed 640 x 520 size and fades in after preferences and fonts load. Confirm the size against the reference code before the desktop build opens this as a separate window.
  - reply (Haiku review): Needs Mujtaba. The reference opens Settings at 640 x 520, so the inventory's 1180 x 760 is not the layout reference. The code also leaves the window resizable with a 640 x 520 minimum, which does not match F10-001's word 'fixed', so the desktop window needs one answer on whether it is locked or resizable.

Question: Should the desktop Settings window be fixed at 640 x 520 as F10-001 states, or open at 640 x 520 and stay resizable with a 640 x 520 minimum as the reference code does (Reviewer A reads F10-001's 'fixed' as the open size and minimum, while Reviewer B treats it as a product decision)?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 19: Desktop Settings window size: opens at 640 × 520 and can be resized, never smaller than 640 × 520 (as the reference code does).
