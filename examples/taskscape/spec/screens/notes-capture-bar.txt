# Review notes on the capture-bar screen (the team's comments and how each was settled)

- [web] Opus (orchestrator): Not in the web version: the capture bar is a desktop window summoned by a global hotkey. On the web, tasks are added by hand in the main window only.
  - reply (Haiku review): Decided. Agreed. The brief has no capture window or screen capture on web and tasks are added by hand in the main window, and every F13 and F14 feature is desktop bar, hotkey or tray behaviour. The capture-bar screen is therefore built for desktop only.
- [web] Haiku critic: The footer-right screenshot ToolbarButton, its screenshot_monitor icon, the Capturing Spinner, the screenshot HotkeyHint and the Cmd+Shift+Enter key action all depend on screen capture, which the web version does not have. Remove them, and decide what replaces the footer-right slot (the web app uploads files to the server, so a file attach control is one option, but the inventory does not establish that). Otherwise the slot has no purpose in the web build.
  - reply (Haiku review): Decided. Nothing replaces the footer-right slot on web, since the capture bar is desktop-only and the screenshot button, its icon, the Capturing spinner and the screenshot HotkeyHint do not carry over. Do not add a file-attach control here; web uploads belong to the main task editor. Desktop keeps the screenshot ToolbarButton, its icon, its HotkeyHint and the Cmd+Shift+Enter binding.
- [desktop] Haiku critic: The inventory shows no widget for the global summon/dismiss hotkey, the click-away dismiss, or the tray entry points, yet the features list (F14-001, F14-024, F14-040 to F14-042) depends on them. The desktop rebuild needs a place in the spec for these entry points, or an explicit note that they live outside this screen.
  - reply (Haiku review): Answered. These entry points live in the tray process, not in this screen's widget tree. The global toggle is registered from hotkey settings (F14-001), click-away dismiss is the window Focused(false) handler with a 500 ms reveal grace, and the tray menu is built in lib.rs:204-216. Add an 'Entry points' note listing F14-001, F14-024 and F14-040 to F14-042, and record the docs-versus-code conflict on show_menu_on_left_click in F14-040; a hotkey pressed while main is focused is handled by main (F14-047).
- [both] Haiku critic: Cmd+Enter does different things depending on focus. In the notes editor it submits (submitOnModEnter), while the global capture-enter feature dismisses when the title is focused (F13-016), and plain Enter in the title saves. Pick one submit model for the same job, and state the outcome of each path in the spec.
  - reply (Haiku review): Needs Mujtaba. Today Cmd+Enter in the title does two jobs: the card save submits, and the global capture-enter dismisses the bar, because Cmd+Return is the default toggle. Reviewer A asks the owner to choose among the three options above, while reviewer B makes plain Enter and Cmd/Ctrl+Enter submit from the title with Escape as the only dismiss key, which removes the title-dismiss branch of the global toggle. The owner needs to pick which key owns this behaviour before the capture-bar spec is final.

Question: Should Cmd+Enter in the title field submit the task or dismiss the bar, given that Cmd+Enter is also the default global toggle: (a) submit from title and notes and move the toggle default off Cmd+Enter, (b) keep Cmd+Enter as the toggle and submit from the title only on plain Enter, with Cmd+Enter submitting only in the notes, or (c) submit from title and notes and ignore the toggle while the bar is focused?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 20: Capture bar, Cmd+Enter (desktop only): while the bar has focus, Cmd+Enter (Ctrl+Enter on Windows) submits from the title or the notes; the global show/hide toggle acts only when the bar does not have focus. Escape dismisses the bar.
- [web] Haiku critic: The Clear ToolbarButton, the target button and the screenshot button all carry tabIndex -1, so keyboard users cannot reach them with Tab (F13-041), and the collapsed Tab-hint button has no focus style. The web build should make these controls tabbable with a visible focus ring, since browser shortcuts take precedence and keyboard reachability is required.
  - reply (Haiku review): Decided. This does not apply to web, because the capture bar is desktop-only. On desktop keep tabIndex -1 on the target, Clear and screenshot buttons as the reference records, since Tab moves only between title and notes and each action has a hotkey. Give the collapsed Tab-hint button the shared library focus ring, since it is a plain button with no focus style.
- [both] Haiku critic: Two ToolbarButtons with the same size xs, well variant use different icon sizes (Clear uses iconSize 16, the screenshot button uses iconSize 15) for no stated reason. The collapsed Tab-hint button also has no hover state while the other footer and title buttons change text colour on hover. Pick one icon size and one hover rule for all ToolbarButtons.
  - reply (Haiku review): Decided. Every xs ToolbarButton uses iconSize 16, so the screenshot button moves from 15 to 16 to match the bar's other icons. All text-style buttons, including the collapsed Tab-hint button, use the content-2 to content-1 hover. The screenshot button's filled state uses the shared neutral filled variant rather than accent, since the brief reserves accent for the primary action and selection.
- [web] Haiku critic: The formatting tooltips show ⌘B, ⌘I and ⌘U, and the Clear tooltip shows ⌘⇧⌫. Because browser shortcuts take precedence in the web build, Cmd+B, Cmd+I and Cmd+U may be taken by the browser, so these hints may be wrong there. The web build needs a shortcut mapping check, and the hint text should follow the shortcut that actually works.
  - reply (Haiku review): Decided. This does not apply to web, because the capture bar is desktop-only. On desktop the hints show the platform modifier, Cmd on macOS and Ctrl on Windows, for Cmd+B, Cmd+I, Cmd+U, Cmd+Shift+Backspace and Cmd+Shift+Enter. The browser-conflict check for B, I and U belongs to the web main-window editor if it reuses this toolbar.
- [desktop] Haiku critic: The bar is a frameless window whose height changes from 116 px to 185 px when the notes open, and it is anchored to the cursor edge (F14-015 to F14-019). The desktop build should resize a separate window and keep its anchor and screen-edge flip logic, which the inventory only describes as card heights. The web build needs none of this, since the capture bar is desktop-only.
  - reply (Haiku review): Answered. The reference already does this in the desktop window: a non-activating frameless panel with an opaque rounded card whose height follows the card, 116 px collapsed and 185 px with notes open, capped at 300 logical px. Placement anchors at the cursor, flips at the right and bottom edges, and is clamped to the display. Keep this logic in the desktop spec and record the ids F14-015 to F14-019, F14-028, F14-031 and F14-032 in the frame note; the web build has no equivalent.
