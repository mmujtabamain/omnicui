# Review notes on the trash screen (the team's comments and how each was settled)

- [both] Haiku critic: The Empty ToolbarButton is specified as variant=danger in TrashPane.tsx, but the captured look shows it in the same grey as Restore all, not red. Pick one: either the destructive action gets its danger tone in both rebuilds, or the variant is dropped so the two bulk buttons match. The inventory should record which one is intended.
  - reply (Haiku review): Decided. Destructive actions show the danger colour at rest in both builds: Empty keeps variant danger (TrashPane.tsx:69-80), per-row Delete permanently gets the same (TrashPane.tsx:116-124), and Restore all stays default. The reference's danger variant renders grey at rest and turns red only on hover (ToolbarButton.tsx:28-29; IconButton.tsx:34), so the grey capture is accurate to the reference rather than stale, and the shared library's danger variant needs a danger-coloured resting state. This is a deliberate change from the reference.
- [both] Haiku critic: Confirmation policy is inconsistent: Empty opens the 'Empty Trash?' sheet (F07-006), but the per-row Delete permanently IconButton calls purge([t.id]) immediately with no confirmation (F07-011). A permanent delete of one item should get the same guard as clearing the whole trash, or the difference should be stated as deliberate.
  - reply (Haiku review): Needs Mujtaba. The reference purges one item at once with no confirmation (TrashPane.tsx:122; F07-011), while Empty asks first through askConfirm (TrashPane.tsx:37-45; F07-006), and purge cannot be undone (F07-012). Neither the brief nor the decisions settles whether a single permanent delete needs a guard, so it goes to you.

Question: Should the per-row 'Delete permanently', which cannot be undone, (a) get the same danger confirm sheet as Empty, naming the item, (b) stay immediate and be recorded as a deliberate exception to the reference, or (c) confirm only when several items or the last item in the trash are purged?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 12: Delete permanently in Trash: immediate for a single row. Purging several items at once, and Empty Trash, ask first, naming how many.
- [both] Haiku critic: The pane title bar's Minimize and Full Screen lights are inert and have no purpose in this pane (F07-082), and the inventory lists no behaviour for them. The rebuild should drop them from the Trash pane title bar; only the close control has a function, and on the desktop build the main-window controls stay with the main window.
  - reply (Haiku review): Decided. Minimize and Full Screen are inert in this pane (WindowControls.tsx:110-111; F07-082), and the Trash pane is a pane rather than a window, so both lights are dropped in both builds. The pane keeps only the red close control, titled 'Close Trash' (F07-081; TrashPane.tsx:61-63). The main window's own controls stay on its title bar (F07-085).
- [web] Haiku critic: Per-row Restore and Delete permanently buttons are opacity-0 until group-hover, so they are invisible to keyboard and touch users. The web build needs focus-visible styling and always-visible or tap-reachable row actions, and the inventory should list a focus state, which none of the row buttons has.
  - reply (Haiku review): Decided. Desktop keeps the reference hover reveal (TrashPane.tsx:112, 121; F07-009). In the web build, the row Restore and Delete permanently buttons show on row hover, on focus within the row and on row selection, stay visible on devices without hover, and get a focus-visible ring since they are real buttons. The inventory's row IconButton entries should add the missing focus state.
- [web] Haiku critic: The Trash pane shortcut hints (Hide preview panel ⌘\, Settings ⌘,) and the ⌘Z hint in the undo notice assume global-style keys. Browser shortcuts take precedence in the web build, so these hints need web-specific bindings or removal, and the inventory should not carry the desktop shortcut text over unchanged.
  - reply (Haiku review): Decided. The Cmd+Backslash and Cmd+, hints sit on the main title bar's Hide preview panel and Settings buttons (F07-092, F07-093), not in the Trash pane, and the Cmd+Z hint is in the Move to Trash sheet detail (tasks.ts:77, 114; F07-079), not in the undo toast. In the web build, drop any hint whose key the browser may take, remove the Cmd+Z text from the web Move to Trash detail, and keep Cmd+Backslash and Cmd+, only where the web app actually receives them. Each build's bindings should be recorded in the spec.
- [web] Haiku critic: The trash is multi-user in the web build, so Restore all, Empty and the row actions can act on items another user has already restored or purged. Feature F07-013 (reconcile with the live task store) and F07-014 (no error handling) are not represented by any widget, and the web build needs a stale-item and failure message on these actions.
  - reply (Haiku review): Needs Mujtaba. The reference reloads both stores after the API call (trashStore.ts:27-30; F07-013), but no handler catches a rejection, so no error is shown (TrashPane.tsx:35-46, 113, 122; F07-014). One reviewer decided the web build should refresh the list with 'This item was already changed elsewhere' for stale items and show an error for other failures, while the other treats the choice as a product call, so it goes to you alongside the toast question in seed-toast-3.

Question: When a web Trash restore or purge is rejected, or the item was already restored or purged elsewhere, should the pane (a) reload the list and show an inline message, (b) reload silently as the reference does, or (c) show a toast with the error, and should the same choice govern the web undo failure in seed-toast-3?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 14: Trash restore or purge fails on the web, or the item changed elsewhere: the Trash reloads its list and shows a short inline message at the top of the pane saying what happened. (Undo failures follow 11.)
