# Review notes on the context-menus screen (the team's comments and how each was settled)

- [web] Haiku critic: Right-click on a task row and on a list tab is only inferred (no onContextMenu in the trees, F06-052 and F07-065 are unverified). In the web build the browser's native context menu and browser shortcuts take precedence, so the right-click opener must be defined explicitly or dropped. The More IconButton (eight per task row) is the only confirmed opener and should be the baseline for web.
  - reply (Haiku review): Decided. Both reviewers agree the reference has right-click on task rows and list tabs, so the 'inferred only' note is stale. There are eight More buttons in total, one per task row in the recording. On web the brief gives browser precedence, so the native menu is not suppressed and More is the opener there; each list tab also gets a More IconButton because the reference tab menu has no visible opener. Desktop keeps right-click, and the other review's suppression of the native menu on web was not followed.
- [both] Haiku critic: The Move to list MenuItem (chevron_right, submenu) has no recorded submenu contents, so the list targets, empty-list state and selection behaviour are unknown. Its open-on-hover-only behaviour (F06-047) also gives no click or keyboard path, so the rebuild needs a defined click/keyboard way to open it and a list of destinations.
  - reply (Haiku review): Decided. The reference submenu lists every list in the active project with no filter, so the task's own list appears there. Decision: the submenu omits the task's own list because moving there is a no-op, and the row is disabled when no other list exists. Clicking Move to list, or pressing ArrowRight or Enter on it, opens the submenu; ArrowRight focuses the first list, Enter on a list moves the task (or the whole selection in bulk), and Escape or ArrowLeft returns to the parent menu. This applies to web and desktop alike.
- [both] Haiku critic: In the project-dropdown, Rename project and Delete project are IconButtons that are opacity-0 until the row is hovered, while the task and tab menus expose Rename and Delete as full text MenuItems always visible. The same job (rename, delete) is done by different widgets, and the hover-only buttons are unreachable by touch or keyboard, so they should match the text-row pattern.
  - reply (Haiku review): Decided. The reference's project Rename and Delete controls are icon buttons at opacity-0 that show only on group-hover, so they stay in the tab order but are invisible unless hovered. Decision: each project row gets a More button that is visible at rest and opens the shared menu with 'Rename project' and 'Delete project' as text items, matching the always-visible text rows of the task and tab menus. The hover-only icon buttons are dropped.
- [both] Haiku critic: Two anchored menu implementations coexist: MenuPanel (ContextMenu.tsx, with a 4px viewport clamp, submenu flip and Overlay dismissal) and the ProjectMenu Surface2 dropdown (no MenuPanel, no Overlay, no clamp or flip recorded, dismissed only by onDismiss). The rebuild should use one menu component so project and task menus share positioning, dismissal and Escape handling.
  - reply (Haiku review): Decided. Both reviews agree on one menu component. Task, tab and project menus all use the MenuPanel pattern with the 4px viewport clamp, submenu flip, Overlay dismissal and Escape handling, and ProjectMenu is rebuilt on it instead of its own useDismissable surface. The inventory also missed five menus on the same layer, which join the same component: Search options, the bulk Move menu, the attachment tile menu, the filter menu and the multi-inspector menu.
- [desktop] Haiku critic: The whole menu layer (full-window Overlay, Backdrop2 scrim, z-order above sheets per ContextMenu.tsx:30-32) is an in-window construct. In the desktop build, task and tab menus should open as native popup menus at the pointer or More button, and the sheet-stacking rule (F06-044) no longer applies because sheets are separate windows.
  - reply (Haiku review): Decided. Desktop menus stay in-window as anchored panels from the shared menu widget, not native OS popups, because the brief gives one widget per job. Each sheet is its own window, so F06-044 (menus above sheets) no longer applies on desktop and the main window never shows a menu over a sheet. The transparent Backdrop2 stays only as an invisible hit area with no dimming.
- [both] Haiku critic: The Copy row has the purpose 'Copies the task' with no target format recorded, while the feature list has F07-053 'Copy tasks as Markdown'. The inventory should state what Copy puts on the clipboard, including the multi-task case, so the rebuild matches the Markdown copy behaviour.
  - reply (Haiku review): Answered. The source answers it: a single-row Copy passes only that task to copyToClipboard, and the bulk 'Copy N tasks' passes the whole selection. The backend renders a Markdown checklist of exactly the given tasks in tree order, indented by selected ancestors only, with notes as '>' lines, so an unselected subtask is left out as F07-053 records. Copy changes no state and an empty selection copies nothing, so the inventory purpose should read 'Copies the task(s) as Markdown to the clipboard'.
- [web] Haiku critic: The project-dropdown Delete project button has no confirmation step recorded (handler 'likely confirmed, not captured'), whereas tab Delete list… routes to a confirmation sheet (F07-073). In the multi-user cloud app, deleting a shared project needs a confirm step and a permission check, which the inventory does not cover.
  - reply (Haiku review): Needs Mujtaba. The reference already has the deletion confirmation: a danger sheet counts the project's lists and tasks before removing it. The reference is single-user with no permission check, and the brief does not settle who may delete or rename a shared project. Both reviews agree this needs a product decision.

Question: Who may delete or rename a shared project in the multi-user web build: (a) only its owner, (b) any member, or (c) the owner and admins?
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 9: Who may rename or delete a project on the web: projects belong to one owner, and only the owner may rename or delete them. Sharing projects between users is out of scope for the first web version.
- [both] Haiku critic: The state name 'multi-context-menu' is a single-row task menu on 'Cut a spare key', and no bulk or multi-selection menu is recorded. Bulk actions exist in the feature list (F07-058 bulk bar, F07-059 to F07-064 Bulk Done, Move to, Copy, Delete, Clear), so the rebuild needs to decide whether a right-click on a multi-selection shows a bulk menu or the single-row menu.
  - reply (Haiku review): Answered. The reference has a bulk menu that the inventory missed. Right-clicking a row inside a selection of two or more shows Copy N tasks, Mark N done, Mark N not done, Move to list (submenu) and Delete N tasks, and keeps the selection; right-clicking an unselected row selects it alone and shows the single-row menu. Bulk delete asks one 'Move N tasks to Trash?' sheet. Add a bulk state to the inventory and drop the 'no multi-selection evidenced' note.
