# Review notes on the title-bar screen (the team's comments and how each was settled)

- [web] Opus (orchestrator): The web has no window controls (traffic lights) and no drag region; the browser owns the window. The project switcher and list tabs stay.
  - reply (Haiku review): Decided. Agreed by both reviewers: on web the browser owns the window, so the title bar has no window controls and no drag region. The project switcher and the list tabs stay, since they are app navigation that does not depend on a native window. The desktop title bar keeps the drag region and the tab-row drag strip, and the reference already splits window controls by platform, with MacLights on macOS and WinControls elsewhere.
- [web] Haiku critic: The drag grip (drag_indicator in a drag-region div) and the header's double-click toggleMaximize behaviour only make sense for a desktop window. In the browser build the grip should be removed, and the bar should not act as a window drag area (F02-001, F02-059, F02-060).
  - reply (Haiku review): Decided. Agreed: the grip is decorative (pointer-events disabled, not a control), and the header double-click calls toggleMaximize, which only makes sense for a native window. The web title bar drops both, and desktop keeps them (F02-001, F02-003), with F02-059 and F02-060 covering window dragging only and going with the desktop build.
- [web] Haiku critic: The macOS traffic-light cluster (MacLights, close, minimize, full screen) and the Windows/Linux WinControls cluster both control a native window. Neither has a web equivalent, so both regions should be dropped on web, along with the blur and focus-driven disc states (F02-023 to F02-028, F02-029 to F02-031).
  - reply (Haiku review): Decided. Agreed by both reviewers: web drops both the MacLights and WinControls clusters, along with their focus-driven disc states, since they call native window methods (close, minimize, fullscreen, toggleMaximize). Desktop keeps them in the form chosen in the seed-main-window-4 question, and the blur and focus states go with the native window. F02-023 to F02-028 are macOS-only and F02-029 to F02-031 are Windows-only.
- [general] Haiku critic: Delete affordances are inconsistent. Each list tab shows a × delete button at all times, but each project row's delete icon is hidden until hover (opacity-0), and lists can also be deleted by middle-click. Hover-only controls will not be reachable on touch screens in the web build, so project delete should get a consistent, always-available form.
  - reply (Haiku review): Decided. The reference is inconsistent: list tab delete is always visible, while project row rename and delete are hidden until hover (opacity-0 group-hover), and middle-click also deletes a list. Both builds make project rename and delete always-visible IconButtons, with the danger variant on delete, matching the list tab, and middle-click stays as a mouse accelerator on both with every delete still confirmed.
- [general] Haiku critic: The Split view button's active state (filled, title "Close split view") and the Swap panes button are not in any recorded state. F02-022 requires filled and inactive-greyed variants by state, so the inventory has no visual reference for the split-on toolbar state.
  - reply (Haiku review): Answered. The split-on state is recorded in the existing split-view recording: the Split view button is active with a filled icon and primary text tone, its title becomes 'Close split view', and Swap panes appears (shown at 1044,8), so the title-bar inventory's 'not in any recorded state' is stale. The rebuild uses the shared IconButton filled and active variant bound to one flag (F02-022), so the behaviour and variant are answered by the code and the recording.
