# Review notes on the task-list screen (the team's comments and how each was settled)

- [both] Opus (orchestrator): Option changes the check from select to done. Keep this mode on both versions; on Windows and the web the modifier is Alt, and the hint text must name the platform's key.
  - reply (Haiku review): Decided. Agreed. Option switches the round check from select to done on both versions, Control or Command selects rows, and the hint names the platform key: 'Option' on macOS, 'Alt' on Windows and the web. The reference already keys the done toggle on altKey, so this mode is kept and the reference's Control wording (F01-085) is overridden by the brief.
- [both] Haiku critic: The search scope choice ('This list', 'Whole project', 'All projects') in the ScopeFields menu has no widget that shows results outside the current list. The match count is described as 'direct' matches, but nothing in the inventory says where indirect matches appear or how the pane shows them. Add a widget or state for cross-list results, or state that the scope only affects the count.
  - reply (Haiku review): Needs Mujtaba. Both reviewers agree the gap is real: the pane renders only the active list's roots, so the wider scopes change the direct-match count but no row from another list can appear. The brief does not say whether cross-list matches should show, so the owner needs to choose one of the three options before the inventory can name a widget for them.

Question: When the scope is Whole project or All projects, how should matches in other lists appear? Options: (a) keep the reference, where the scope changes only the match count and rows stay in this list; (b) add a cross-list results section to the pane; (c) keep the count but drop Whole project and All projects from the menu.
  - reply (Opus (orchestrator)): Decided with Mujtaba (14 Nov), decision 3: Search beyond this list (redesigned): when the search scope is Whole project or All projects, the pane shows the matches grouped by list, each group headed by its list (and project) name. Choosing a match opens that list with the task selected and previewed. The match count counts every group. This replaces the reference, where the scope changed only the count.
- [both] Haiku critic: The two popover menus are anchored with different offsets for no stated reason: the Search options menu sits at bottom + 6, while the row More menu sits at bottom + 4. Use one anchor offset for both popovers.
  - reply (Haiku review): Decided. Decided: every popover anchored to a button uses bottom + 4, set once in the shared popover component. The reference already uses +4 for the row More menu, the bulk Move menu, the Filter panel and the multi-inspector, so only the Search options menu changes from +6 to +4.
- [both] Haiku critic: The same bulk job has different names across widgets. The row menu says 'Move to list' and 'Delete task…', the BulkBar says 'Move to…' and 'Delete', and the Done and Undone toolbar titles ('Mark done', 'Mark not done') differ from their labels. Pick one vocabulary for move, delete and done, and use it in the menus, the bulk bar and their titles.
  - reply (Haiku review): Decided. Decided: one verb per job across menus, the bulk bar and titles. Moving is 'Move to list' to match the existing row-menu label (the bulk 'Move to…' becomes 'Move to list' with the same title), marking done is 'Mark done' and 'Mark not done', and deletion is 'Delete', with the trash confirmation's accept button reading 'Delete' while its 'Move to Trash?' headline stays. Reviewer B's 'Done'/'Undone' and 'Move to…' wording is not adopted because it would change the existing row-menu and count labels.
- [web] Haiku critic: The search field takes Cmd+F and typed letters to focus search (registerSearchFocus, feature F01-013). In the browser Cmd+F is the browser find shortcut, and the spec says browser shortcuts take precedence, so the web search field should not claim Cmd+F. Keep only the in-page focus path, such as a '/' key or the field itself.
  - reply (Haiku review): Decided. Decided: remove Cmd+F from the web search field, because browser shortcuts take precedence on the web. The field stays clickable and the plain typed-letter seed stays because it is not a browser shortcut; no '/' key is added because the reference has no such binding.
- [web] Haiku critic: The empty-state subtitle 'Press + or ⌘N to add a task, or ⌘↩ anywhere to capture one' refers to a capture bar and global hotkeys that the web version does not have. The web empty state should say only how to add a task by hand, such as the '+' New task button. The desktop version can keep the capture hint.
  - reply (Haiku review): Decided. Decided: the web uses the no-capture-hint empty state with the subtitle 'Press + to add a task', dropping the Cmd+N part too because browser Cmd+N opens a new window and the web has no global hotkeys. The desktop keeps the capture-hint variant (F01-017).
- [both] Haiku critic: The title and notes highlight (mark element) is always applied to both fields, per feature F01-040, but the ScopeFields 'Title only' and 'Notes only' choices limit matching. A 'Title only' search therefore highlights note text that did not match. Make the highlight follow the fields setting, or document the difference in the inventory.
  - reply (Haiku review): Decided. Decided: keep the reference behaviour, where the title and notes highlight regardless of the fields setting, and record it on the inventory. Rows and the match count follow the fields setting through the search set, but reviewer B did not read isVisibleInPane, so the inventory should mark that link as unverified until it is read.
