# P0: the contracts, the shared spec and the tauri target

Run this first: P1 and P2 build on what P0 writes.

## Shared by all three prompts

You are one of three agents building Taskscape as an omnicui example. Taskscape is a macOS task manager built as Tauri v2 apps (React 19 and Tailwind v4 in a webview, Rust behind). It is being ported to a native GPUI app (Zed's Rust UI framework) and to a web app. The UI design is mostly final.

omnicui checks two things:
- that the versions behave the same;
- that they keep one consistent design, while each is idiomatic for its platform and uses what that platform does best.

**Where things are**, in the omnicui repository:
- `examples/taskscape/tauri/`: the Tauri app, the reference. Read its AGENTS.md, `.llm/*.md` and `docs/main-app-design-review-2026-08-13.md`. The design direction agreed there starts at "Direction From Your Answers". Some file names in `.llm/main-app.md` are out of date: trust `main/src`.
- `tools/omnicui/`: omnicui itself. Never edit it. Build it once: `cd tools/omnicui && go build -o ../../bin/omnicui ./cmd/omnicui`.
- Read:
  - README.md;
  - docs/SPEC.md §1, §4.2, §4.2a (what may differ by platform), §4.3, §4.4 (the protocol), §4.8 and §5;
  - `examples/todo/`: one product, idiomatic per platform, checked by one set of contracts. Its PROCESS.md says what went wrong there;
  - `docs/verification/mobile-review/README.md`: an earlier agent's mistakes. Don't repeat them.

**Folders** (all under `examples/taskscape/`):
- **P0** owns `omnicui/`: the omnicui project, with its contracts, `platforms.yaml`, fixtures, `SPEC-PRODUCT.md`, `DESIGN.md` and `targets/tauri`. In `tauri/` it may add part tags (`data-part` attributes) and a component registry entry point. Nothing that changes behaviour.
- **P1** owns `gpui/` and `omnicui/targets/gpui/`.
- **P2** owns `web/` and `omnicui/targets/web/`.

Never edit another agent's folder. P1 and P2 never edit the contracts, `platforms.yaml`, `SPEC-PRODUCT.md` or `DESIGN.md`. Where those are wrong or too strict, write it in your GAPS file, with what you would have wanted, and say so in your report. P0 decides.

**How to work:**
- Work in focused runs: `omnicui check <target> <component>`, `--test`, `--failed`. Run a full `check` at most three times, at milestones.
- Never fake a part or an event to get a pass, and never weaken a test to make one pass.
- Keep `PROGRESS.md` in your folder current: a few lines per milestone, with the time. If you are stopped, whoever resumes you reads it.
- At each visible milestone, take a screenshot and share it as your environment says. Keep the image files out of the repository.
- Don't commit. Whoever runs you reviews and commits your folder.
- Name no host, service or workspace in any file you write.
- End with a report. Put it in your GAPS file:
  - what omnicui or the contracts got in your way, and what you would have wanted to write;
  - the last full check's summary line;
  - start-up and total time per target;
  - your own mistakes, marked as such.

## The task

1. Inventory the main window (tauri/main/src, tauri/common-ui/src) and the tray's capture bar (tauri/tray/src).
   Cover:
   - the title bar;
   - the project switcher and list tabs;
   - the task pane: rows, completion, nesting, inline add, reordering, the context menu;
   - the preview rail: task inspector with rich-text notes and attachments, draft and multi
     inspectors;
   - the filter panel and trash;
   - the command palette;
   - sheets and toasts;
   - the Settings window: general, capture, shortcuts, about;
   - the attachment lightbox;
   - the capture bar.
   Rank them by how much of the product they carry. The contracts must cover the top of that
   list well rather than everything thinly.
2. Choose components the way omnicui mounts them, one per surface, each mountable from props.
   Keep a sheet or the palette as a component of its own, not a part of the window.
   - Props are primitives only. Use a `seed` prop (enum) that selects a fixture.
   - Fixtures go in examples/taskscape/omnicui/fixtures/*.json: projects, lists, tasks with nesting, notes,
     attachments. Each fixture loads through taskscape_common's `Store` into a fresh temporary
     database, so every version reads the same data the same way. Write the loader (a small
     Rust binary or library in examples/taskscape/omnicui/fixtures/) and use it in your target.
   - Events are what a user action changes, named for the domain, for example:
     `taskCreated {id, title, listId}`, `taskCompleted {id, done}`, `taskMoved`, `listCreated`,
     `noteChanged`, `hotkeyChanged`.
   - Parts are named for meaning, with WAI-ARIA roles.
3. **Named inputs.** Write platforms.yaml from the hotkey catalog (tauri/common/src/hotkeys.rs and
   tauri/common-ui/src/hotkeys.ts): new task, capture, the palette, delete, navigation between lists.
   A desktop app on macOS uses ⌘; the web must not take the browser's own shortcuts (⌘N, ⌘T,
   ⌘W, ⌘L) and needs alternatives. Use target selectors `tauri`, `gpui`, `web` where the forms
   differ.
4. **Tests.** Behaviour first, with strong oracles: exact text, state and events.
   - Use `keyboard: true` where it makes sense, screenshots light and dark, and traces or
     records where the design animates (the panel-in and rise animations, sheets, toasts).
   - Use `only:` for what exists on desktop only: the custom title bar, window controls, the
     capture bar.
5. **Design.** Write DESIGN.md for the porters:
   - the tokens from tauri/common-ui/styles/tokens.css, converted from oklch to sRGB hex for GPUI,
     light and dark;
   - the type scale (the app uses the system UI font) and the spacing, radii and elevation;
   - motion: the durations and easings in tokens.css;
   - the window's structure and proportions at 1180×760 (the default in
     tauri/main/src-tauri/tauri.conf.json);
   - for every control, whether each platform draws it natively or from the tokens.
   "Consistent but idiomatic" is the rule.
   - In the contracts, set the contract-level `same: [layout, colours, motion]`.
   - Loosen per part where a platform draws its own control or chrome, and say why in a comment:
     the title bar, window controls, text fields, menus, scrollbars.
   - Hold the product's own surfaces to layout, colours and motion: task rows, the inspector,
     the palette, empty states.
   - Viewports: 1180×760 for desktop, plus one narrower web size if the web port is meant to be
     responsive (agree it with P2).
6. **SPEC-PRODUCT.md** is for P1 and P2: every component, its props, fixtures, events, parts
   (role and meaning), behaviour rules, texts, and what each platform is free to do. Make it
   precise enough to build from without reading the React code, and use the design review's
   direction where the current app hasn't caught up.
7. **targets/tauri.** The Tauri app's real frontend, driven in Chromium with Playwright, since
   macOS's WKWebView has no WebDriver.
   - Mount components from a registry page. Route `@tauri-apps/api` calls with Tauri's
     `mockIPC` to a real `taskscape_common::Store`, through a small Rust server you write on a
     temporary database seeded from the fixtures. No in-memory fake of the commands.
   - target.yaml: `design: tauri`, `platform: [desktop]`.
   - Report the host OS in advertise, and the custom title bar region in each screenshot reply.
   - Measure start-up. Don't start a build per check: build once with a setup script.
8. Run until the tauri target passes every contract. Then report that P1 and P2 can start, with the inventory and links to DESIGN.md and
   SPEC-PRODUCT.md.
