Platform / target limits (reported honestly in advertise.cannot)
1. key and focus: UIKit's public in-process APIs cannot inject hardware key
   events or move hardware focus to arbitrary SwiftUI accessibility elements.
   UITextInput inserts actual text, a character at a time; it is not used to
   pretend that Space/Enter was delivered to a button or switch. Consequently,
   the keyboard tests, including Enter in the add field, are unadvertised. The
   shipping app keeps the platform's native keyboard behavior and onSubmit.
   Wanted: an iOS automation API that delivers real keyboard input in-process.
   This is a platform limit, not a contract error.
2. Drag, hover, per-frame trace and recording are not implemented. Trace and
   recording are this target's omissions, not claims that iOS cannot do them.
   They are unadvertised; none of the supplied behavior tests needs them.
3. The host enables Apple's lazily loaded accessibility runtime through
   _AXSSetAutomationEnabled. This private Simulator test-host dependency is
   confined to the target. The shipping app/framework use public APIs. Reads
   then use live UIKit accessibility objects, not XCTest snapshots.
   Wanted: a public API to enable/access SwiftUI's in-process accessibility tree.
4. The 360x640-point hosting window is rendered directly at renderer scale 1.
   SpringBoard's status bar and home indicator are outside that window; they
   are not drawn and are not falsely reported as screenshot regions. Visible
   UIKit input windows are composited at their native point frames and their
   intersecting keyboard region is reported if drawn. The checked Simulator
   configuration did not show a software keyboard; captured replies therefore
   have regions: []. This is distinct from the standalone app, which displays
   the normal device status bar and home indicator.
5. Native edge-pop is enabled in the app. Protocol do.back activates the named
   native navigation control (or dismisses the presented add sheet). The button
   and modal-back paths are verified. Finger swipe input is not injected by
   this target, so the physical edge gesture itself was not automated.

OWN mistakes (fixed; not omnicui bugs)
- Wrong swiftc linker flag and initialization order in the first build.
- First advertise omitted mount/read/events, so the first focused test was
  correctly unadvertised. Fixed before any full check.
- A Swift protocol cast missed dynamically exposed accessibility identifiers;
  the adapter now asks the runtime object's actual identifier getter.
- I initially treated toolbar controls and virtual segments like ordinary
  SwiftUI buttons. The adapter now dispatches their native UIControl actions.
- I initially drew a presented sheet separately, producing black areas and an
  incorrect window size. Rendering the viewport-sized native window fixed it.
- FocusState belonged in the sheet, not the presenting list. Moving it fixed
  the required initial text-field focus without synthesizing a read value.
- My absent-part bounds path logged too much while diagnosing an empty list.
  It now returns the protocol's zero-size bounds for an unrendered part.
- I embedded UIHostingController under an extra plain UIKit controller, which
  blocked preferredColorScheme from changing the rendered theme. Mounting it
  as the window root fixed the appearance, verified from light-to-dark captures.
- Native switch accessibility nodes needed association with their UISwitch
  backing view to distinguish a switch from a toggle-style checkbox.
