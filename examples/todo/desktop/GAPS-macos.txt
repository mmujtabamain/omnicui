What omnicui/contracts could not check
1. keyboard: true has no per-part setup. Its dialog Add and Cancel tests mount
   the list with the dialog closed, then report "not measured". It suggests
   adding a component or a prop that mounts the dialog shown, which would change
   this product API. Neither the app defaults nor the contracts were changed
   to accommodate that suggestion.
   What I wanted to write (proposed syntax, not currently accepted):
     keyboard:
       confirmAdd:
         setup: [{action: press, part: add},
                 {action: type, part: newTitle, text: Keyboard task}]
         keys: [Enter, Space]
       cancelAdd:
         setup: [{action: press, part: add}]
         keys: [Enter, Space]
2. The generated All/System segment tests have no observable change from the
   default mount. They are also "not measured", rather than testing the segment
   after choosing another one. I wanted per-part keyboard setup steps for that
   state as well. Together these limitations cause 16 not-measured results
   across the two targets; they are not missing adapter capabilities.
3. SPEC-APP section 7 asks for Enter and Space on checkboxes and switches, but
   generated checks exercise only Space for those roles. I wanted contract
   keyboard configuration that explicitly enumerates both keys per role.
   The adapter accepts both. The independent smoke test also exercises Return
   on a switch and dialog Add/Cancel after the normal user setup.

What omnicui got in my way
- No blocking protocol, titlebar, layout, colour or motion comparison defects.
- The generated keyboard tests cannot set up a dialog or an alternate selected
  segment, and do not generate Enter checks for switches/checkboxes. The
  desired contract additions are written above; no tool/contract workaround
  was added, and the 16 unmeasured results remain visible.

Own mistakes (corrected)
- I initially read @Published tasks before the store was fully initialized,
  and used an unavailable Swift spelling for the heading accessibility role.
  Both were compile-time mistakes, fixed before any full check.
- I initially serviced stdin without NSApplication.run(). That produced
  inactive native controls and incomplete accessibility behavior. Requests
  now run on the main queue inside the real application event loop.
- I initially relied on native button content tint to colour button titles;
  AppKit did not apply it consistently. Attributed native titles now use the
  product palette, including the dark on-accent colour.
- The first notes field wrapped text but was not a proper multiline editor.
  Replaced it with NSTextView; multiline input and per-keystroke events pass
  the independent smoke test.
- My initial toolbar custom views used manual child frames and aligned their
  contents inconsistently. The user identified this. Auto Layout now centres
  both item contents, and Settings keeps its icon and title together.
